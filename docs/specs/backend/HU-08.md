# HU-08 (backend) — Registrar, editar y eliminar producciones

> **Jira:** `TS-19` · **Sprint:** 2 · **Cubre:** RF-02 (alta, edición y borrado), RNF-01 (control de acceso)
> **Contraparte:** `../frontend/HU-08.md` (pendiente de `ts-08.05`)
> **Estado:** `[x]` borrador · `[x]` aprobada · `[ ]` implementada

Los criterios de aceptación de la historia —asociación obligatoria a un artista existente, formato asignado e identificador generado por el sistema— viven en Jira. Esta spec define el contrato backend y los tests que los traducen.

## 1. Alcance en esta capa

**Dentro:**

- `POST /api/v1/productions`: el productor registra una producción para un artista `invitado` o `activo`.
- `GET /api/v1/productions/{production}`: el productor consulta una producción para precargar la edición.
- `PUT /api/v1/productions/{production}`: el productor edita el nombre y el formato; la asociación con el artista es inmutable.
- `DELETE /api/v1/productions/{production}`: el productor elimina lógicamente una producción.
- Tabla, modelo, enum, relaciones, Policy, Form Requests, Service y API Resource de `productions`, conforme al ERD aprobado.
- Respuestas D3.1 para 401, 403, 404 y 422.

**Fuera / diferido (con motivo):**

- Listado de artistas con sus producciones → `TS-17` (HU-06). Esta HU expone el recurso singular, no un `index` de producciones.
- Reglas por cantidad de canciones para `sencillo`/`ep`/`album` → `TS-20` (HU-09). En S2 aún no existe `songs`; aquí solo se valida que el formato pertenezca al enum.
- Canciones y cascada lógica hacia canciones/versiones → HU-10/HU-12 (S3). En esta HU el borrado lógico afecta únicamente a la producción.
- Portada, duración total, cantidad de canciones, porcentaje de avance y cualquier otra métrica derivada → excluidos por Jira y `modelo-sprint-2.md` §5.1.4.
- Reasignar una producción a otro artista → fuera por decisión humana del 2026-10-07. `artist_id` queda inmutable después del alta para no reescribir propiedad, accesos ni historial futuros.
- Rate limiting → D8.5 sigue `ABIERTO`; esta API es compatible con cualquier decisión posterior y no queda bloqueada.

## 3. Contrato técnico

### 3.1 Rutas

Todas las rutas van bajo `api/v1`. Las que reciben `{production}` usan `whereUuid('production')`.

| Método y ruta | Middleware | Éxito |
| --- | --- | --- |
| `POST /api/v1/productions` | `auth:auth0-api`, `can:create,App\Models\Production` | **201** + `ProductionResource` |
| `GET /api/v1/productions/{production}` | `auth:auth0-api`, `can:view,production` | **200** + `ProductionResource` |
| `PUT /api/v1/productions/{production}` | `auth:auth0-api`, `can:update,production` | **200** + `ProductionResource` |
| `DELETE /api/v1/productions/{production}` | `auth:auth0-api`, `can:delete,production` | **204**, sin cuerpo |

- La autorización vive en middleware `can:` para que el inventario de `ApiRouteProtectionTest` la observe. Los Form Requests no la duplican.
- La edición usa **PUT** con la representación editable completa: `name` y `format`. No se publica `PATCH`.
- `artist_id` solo forma parte del alta. Si el cliente lo envía en el `PUT`, se ignora junto con cualquier otro campo ajeno al contrato.
- Un id de ruta que no sea UUID responde 404 y nunca llega como UUID inválido a PostgreSQL.

### 3.2 Autorización — `ProductionPolicy`

`create`, `view`, `update` y `delete` permiten únicamente `Role::Productor`, leyendo el rol desde `StatelessUserContract`, igual que `ArtistPolicy`.

- Un usuario sin identidad válida recibe 401.
- Un usuario autenticado con rol `artista` —o sin rol reconocido— recibe 403 sobre una producción existente.
- Laravel resuelve el route model binding antes de `can:`. Por ello, un rol sin permiso que use un UUID inexistente puede observar 404; se conserva el precedente aceptado por HU-05.
- El estado del artista dueño no cambia esta autorización: el productor puede consultar, editar y eliminar una producción ya existente aunque el artista pase a `inactivo`.

### 3.3 Entrada

#### `StoreProductionRequest`

| Campo | Reglas | Normalización |
| --- | --- | --- |
| `artist_id` | obligatorio, UUID, artista vigente existente | Recortado; no cambia después del alta. |
| `name` | obligatorio, string, máx. 255, único dentro del artista entre producciones vigentes sin distinguir mayúsculas | Recortado; conserva el casing escrito. |
| `format` | obligatorio, valor de `ProductionFormat`: `sencillo`, `ep` o `album` | Recortado; se persiste el valor backed. |

#### `UpdateProductionRequest`

| Campo | Reglas | Normalización |
| --- | --- | --- |
| `name` | obligatorio, string, máx. 255, único dentro del artista dueño entre producciones vigentes sin distinguir mayúsculas; excluye la propia producción | Igual que en el alta. |
| `format` | obligatorio, valor de `ProductionFormat` | Igual que en el alta. |

Reglas comunes:

- Un artista con soft delete se considera inexistente para el alta.
- El mismo nombre puede existir para artistas distintos.
- Una producción borrada libera el nombre para su artista; una producción vigente no.
- `id`, `artist_id` en edición, `deleted_at`, timestamps y cualquier campo extra se ignoran. El Service recibe únicamente los campos expresamente validados/seleccionados.
- Los mensajes visibles salen en español, siguiendo la configuración introducida por HU-05. Los duplicados usan mensajes de dominio: «Ya existe una producción con ese nombre para este artista.».

### 3.4 Regla de negocio sobre el estado del artista

Decisión humana del 2026-10-07:

- Se permite registrar producciones para artistas `invitado` y `activo`.
- Se rechaza registrar una producción para un artista `inactivo` con 422 `VALIDATION_ERROR`, `errors.artist_id` y el mensaje «No se puede registrar una producción para un artista inactivo.».
- La regla se evalúa en `ProductionService`, no en la Policy: el productor sí tiene permiso, pero el estado actual del recurso hace inválida la operación.
- Si un artista pasa a `inactivo` después del alta, sus producciones existentes continúan consultables, editables y eliminables por el productor.

### 3.5 Negocio — `ProductionService`

- `createProduction(datos)`:
  1. Resuelve el artista vigente indicado por `artist_id`.
  2. Rechaza el alta si su estado es `inactivo` (§3.4).
  3. Crea la producción únicamente con `artist_id`, `name` y `format`; el UUID lo genera `HasUuids`.
- `updateProduction(production, datos)` modifica únicamente `name` y `format` y conserva `artist_id`.
- `deleteProduction(production)` ejecuta soft delete sobre esa producción. No borra ni modifica el artista y no intenta cascadas a tablas futuras.

No se introduce una interfaz para el Service: es dominio propio y D4.3 reserva los contratos para fronteras externas.

### 3.6 Persistencia y relaciones

- `Production` usa `HasFactory`, `HasUuids` y `SoftDeletes`.
- `format` se castea a `ProductionFormat`, enum backed con casos `Sencillo`, `Ep` y `Album` y valores definidos por el ERD.
- `Production::artist()` es `BelongsTo<Artist, Production>`.
- `Artist::productions()` es `HasMany<Production, Artist>` y, por el scope de `SoftDeletes`, devuelve solo producciones vigentes salvo petición explícita de lo contrario.
- `ProductionFactory` crea por defecto un artista vigente y datos en español; sus states cubren los tres formatos cuando los tests los necesiten.

La migración `create_productions_table` implementa exactamente `modelo-sprint-2.md` §5.2 y tiene una sola intención:

- PK UUID.
- FK `artist_id` sin `ON DELETE CASCADE`, más su índice no parcial explícito.
- `name`, `format`, timestamps y `deleted_at` con los tipos/nulabilidad aprobados.
- `CHECK` cerrado de formato.
- Índice único parcial `(artist_id, lower(name)) WHERE deleted_at IS NULL`.
- `down()` elimina únicamente `productions`.

### 3.7 Salida — `ProductionResource`

La envoltura es `data`.

```json
{
  "data": {
    "id": "9d3c…-uuid",
    "artist_id": "9d3b…-uuid",
    "name": "Sesiones del álbum",
    "format": "album",
    "created_at": "2026-10-07T14:03:11+00:00",
    "updated_at": "2026-10-07T14:03:11+00:00"
  }
}
```

- Las claves son exactamente las mostradas.
- Las fechas usan ISO 8601 con offset explícito (D3.2).
- No se exponen `deleted_at`, datos del artista, métricas derivadas ni campos futuros de canciones/audio.
- La representación anidada que consumirá TS-17 se definirá en la spec backend de HU-06; no se adelanta aquí.

### 3.8 Errores (D3.1)

Los construye el manejador central. Ningún controlador formatea errores.

| Situación | HTTP | `code` |
| --- | --- | --- |
| Sin token o token inválido | 401 | `UNAUTHENTICATED` |
| Rol `artista` o rol desconocido | 403 | `FORBIDDEN` |
| Producción inexistente, borrada o id de ruta no UUID | 404 | `RESOURCE_NOT_FOUND` |
| `artist_id` ausente, no UUID, inexistente o de artista borrado | 422 | `VALIDATION_ERROR` + `errors.artist_id` |
| Artista `inactivo` al crear | 422 | `VALIDATION_ERROR` + `errors.artist_id` |
| Nombre ausente, vacío, no string, demasiado largo o duplicado | 422 | `VALIDATION_ERROR` + `errors.name` |
| Formato ausente o fuera del enum | 422 | `VALIDATION_ERROR` + `errors.format` |

**Residual documentado:** dos escrituras simultáneas con el mismo nombre para el mismo artista pueden superar la validación y competir en el índice parcial. PostgreSQL impide el duplicado, pero la segunda petición puede terminar como 500 `INTERNAL_ERROR`. Se acepta bajo el supuesto vigente de un único productor (D8.1), igual que el residual documentado por HU-05.

## 5. Notas de implementación para el humano

- Orden sugerido de Green: enum/modelo/factory/relaciones → migración y tests de esquema → Policy/rutas → Form Requests → Service → Resource/Controller → suite completa.
- La regla de artista `inactivo` pertenece al alta del Service. No debe contaminar `ProductionPolicy`, `update` ni `delete`.
- Para la unicidad sin distinguir mayúsculas, seguir el patrón ya revisado de `UniqueArtistName`, pero acotado por `artist_id`; excluir la propia producción al editar y filtrar `deleted_at IS NULL`.
- El índice único parcial con `lower(name)` y el `CHECK` requieren SQL explícito, igual que los índices de artistas. Sus nombres exactos viven en el ERD.
- `DELETE` devuelve `response()->noContent()` después del soft delete; no usa `ProductionResource`.
- `ProductionResource` convierte fechas con `toIso8601String()`, como `ArtistResource`.
- No crear `ProductionServiceInterface`: D4.3 no permite interfaces genéricas del dominio.
- Cadena de calidad: `sail pint --test` → `sail php vendor/bin/phpstan analyse --memory-limit=2G` → `sail pest`.
- `graphify` está instalado, pero `graphify-out/graph.json` no existe todavía. La consulta previa falló de forma explícita y se usó lectura dirigida del código vigente.
