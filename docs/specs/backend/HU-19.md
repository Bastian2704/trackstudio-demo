# HU-19 (backend) — Navegar al comentario y eliminar los propios

> **Jira:** `TS-30` · **Sprint:** 5 · **Cubre:** RF-05 (comentarios), RNF-01 (control de acceso)
> **Contraparte:** `../frontend/HU-19.md` (`ts-19.05`, pendiente). **Antes:** HU-18 ([`HU-18.md`](HU-18.md)). **Sigue:** parte B de HU-21 (`TS-32`, el artista comenta y borra los suyos)
> **Estado:** `[x]` borrador (2026-11-25) · `[x]` aprobada (2026-11-25) · `[ ]` implementada

Los criterios de aceptación (salto a la marca, cada usuario borra solo los suyos, comentarios no editables) viven en Jira. El salto es solo del frontend. Esta spec define el borrado, la ausencia de edición y el dato que el frontend necesita para mostrar el botón solo en los comentarios propios. No hay migraciones: `comments` nació en HU-17 (ERD §3.6).

## 1. Alcance en esta capa

**Dentro:**

- `DELETE /api/v1/comments/{comment}`: borrado físico, solo del autor.
- `CommentPolicy::delete` y el binding de `{comment}`, que oculta los comentarios de versiones borradas (§3.2).
- `is_mine` en cada elemento del listado de HU-18 (§3.5).
- Que no exista ninguna ruta de edición de comentarios, verificado con un test (§4 #7).

**Fuera / diferido (con motivo):**

- Salto a la marca (también tras renovar la URL), confirmación, foco y error → spec frontend (`ts-19.05`). El backend no participa en el salto.
- El artista borra los suyos → parte B de HU-21 (`TS-32`). Hasta entonces recibe 403, como dice D8.1. La ruta y la firma de la Policy quedan preparadas.
- Borrar comentarios ajenos (moderación del productor) → no lo pide ningún AC, y D8.1 dice «solo los suyos» para los dos roles.
- Borrado lógico o papelera → D4.5 no incluye `comments` (ADR, fila «`comments`: no se pueden editar y se borran físicamente»).
- Rate limiting → D8.5 sigue `ABIERTO`. El endpoint es compatible con cualquier salida.

## 2. Dependencias

- **ABIERTOS que no bloquean:** 8.5 y 11.5.

- **Sin dependencias nuevas** de Composer ni externas.

## 3. Contrato técnico

### 3.1 Ruta

| Método y ruta | Middleware | Éxito |
| --- | --- | --- |
| `DELETE /api/v1/comments/{comment}` | `auth:auth0-api`, `can:delete,comment` | **204** sin cuerpo |

- `whereUuid('comment')`.
- La ruta no cuelga de la versión: el id del comentario basta, y así no hace falta un binding con ámbito (`scopeBindings`) ni comprobar que el comentario es de esa versión (propuesta, §6).
- No hay `PUT` ni `PATCH` sobre comentarios (AC «no editables»).

### 3.2 Binding de `{comment}` — comentarios ocultos

`comments` no tiene `deleted_at` (ERD §3.6, I5). Un comentario cuya versión está borrada de forma lógica sigue en la tabla, pero está oculto con ella. El binding lo resuelve solo si su versión existe y no está borrada:

- `Comment::resolveRouteBinding` con `whereHas('version')`. `Version` usa `SoftDeletes`, así que `whereHas` ya excluye las borradas.
- Cubre también las canciones y producciones borradas: su cascada (`SongService::deleteSong`, `ProductionService::deleteProduction`, D4.5) borra antes las versiones.
- Resultado: comentario inexistente, id no UUID u oculto → **404 `RESOURCE_NOT_FOUND`** para cualquier rol, antes de la Policy. Así un comentario oculto no responde 403 a unos y 404 a otros (propuesta, §6).
- No se comprueba `upload_status`: solo hay comentarios sobre versiones `verificada` (HU-17 §3.5), y una versión verificada no cambia de estado.

### 3.3 Autorización — `CommentPolicy::delete`

- `delete(StatelessUserContract $user, Comment $comment): bool`: rol `Productor` **y** autor del comentario.
- **Autor:** `$comment->author->auth0_sub === (string) $user->getAuthIdentifier()`. Se compara el `sub` del token con el usuario local del comentario. No hace falta `firstOrCreate`: quien no tiene usuario local no es autor de nada.
- **Un comentario ajeno responde 403 `FORBIDDEN`**, no 404 (propuesta, §6). El productor ya ve todos los comentarios de la versión en el listado de HU-18, así que esconder que existe no protege nada.
- La parte B de HU-21 cambia la primera condición a «productor **o** artista con acceso vigente a la producción del comentario». La condición de autor no cambia.
- Sin token → 401. `artista` (con o sin acceso, incluso si es el autor) o rol desconocido → 403.

### 3.4 Reglas de negocio — `CommentService::deleteComment(Comment $comment): void`

1. **Borrado físico:** `$comment->delete()`. `Comment` no usa `SoftDeletes`.
2. **Sin cascada:** nada depende de `comments`.
3. **Un segundo `DELETE` del mismo id responde 404** por el binding. No se finge idempotencia con un 204.
4. Se mantiene el método en el Service aunque sea una línea, por D4.4 (el controlador no toca Eloquent).

El controlador devuelve `response()->noContent()`, como `SongController::destroy`.

### 3.5 `is_mine` en el listado (propuesta, §6)

`/me` solo devuelve `sub` y `role`, y el listado no expone el `auth0_sub` del autor (ni debe). Sin un dato del backend, el frontend no puede saber cuáles comentarios son suyos.

- `CommentResource` añade `is_mine` (boolean), **solo cuando `author` viene cargado**: `$this->whenLoaded('author', fn (): bool => $this->resource->author->auth0_sub === $request->user()?->getAuthIdentifier())`.
- Aparece en el listado de HU-18, que ya carga `author.artist`. No añade consultas, así que el test de N+1 de HU-18 (#7) sigue igual.
- **El `201` de HU-17 no cambia:** sigue con sus seis claves, porque no carga `author`. El frontend no lo necesita, ya que tras crear vuelve a pedir el listado (`CommentForm.tsx`, `invalidateQueries`).
- Cada elemento del listado pasa de siete a **ocho** claves: el test #1 de HU-18 se actualiza (§4 #9).

### 3.6 Errores (D3.1)

No se añaden códigos al catálogo.

| Situación | HTTP | `code` |
| --- | --- | --- |
| Sin token o token inválido | 401 | `UNAUTHENTICATED` |
| Comentario inexistente, id no UUID, o versión, canción o producción borradas | 404 | `RESOURCE_NOT_FOUND` |
| Rol `artista` (con o sin acceso, aunque sea el autor) o desconocido | 403 | `FORBIDDEN` |
| Productor que no es el autor | 403 | `FORBIDDEN` |

Precedencia: 401 → 404 del binding → 403.

## 4. Criterios de aceptación de esta capa → tests

Feature tests de Pest contra PostgreSQL con `RefreshDatabase`. Reutilizan `impersonarToken`, `claimsDeToken`, `usuarioDelToken`, `exigirRuta`, `artistaConAcceso`, `versionParaComentar`, `CommentFactory` y los servicios de borrado de canción y producción para la cascada. ## 5. Notas de implementación para el equipo

- Orden sugerido de Green: ruta → `Comment::resolveRouteBinding` → `CommentPolicy::delete` → `CommentService::deleteComment` → `CommentController::destroy` → `is_mine` en `CommentResource` → suite completa.
- Binding: `public function resolveRouteBinding($value, $field = null)` en `Comment`, con `$this->whereHas('version')->where($field ?? $this->getRouteKeyName(), $value)->first()`. Si devuelve `null`, Laravel responde 404 y D3.1 lo formatea.
- Policy: `$user->getAttribute('role') === Role::Productor && $comment->author->auth0_sub === (string) $user->getAuthIdentifier()`. Conviene un `private isAuthor()` para que la parte B de HU-21 solo cambie la condición de rol.
- `is_mine` en el Resource: con `whenLoaded('author', …)`, junto a `author`. `$request->user()` ya es el `StatelessUserContract` del guard.
- Cadena de calidad: `sail pint --test` → `sail php vendor/bin/phpstan analyse --memory-limit=2G` → `sail pest`.
