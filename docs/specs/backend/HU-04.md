# HU-04 (backend) — RBAC y el 403

> **Contraparte:** [`../frontend/HU-04.md`](../frontend/HU-04.md)

Este 403 es la **primera evidencia auditable de RNF-01** para la Sprint Review. La meta a nivel de historia (un `artista` recibe 403 al escribir; sin token → 401; un test por caso) vive en Jira; aquí va el contrato de backend y sus tests.

## 1. Alcance en esta capa

**Dentro:**
- Migraciones del modelo mínimo aprobado en `TS-54`: únicamente `users` y `artists`.
- Una regla de autorización para que el rol `artista` no pueda ejecutar una acción reservada a `productor` (`TS-15`, `ts-04.03`).
- Un endpoint técnico sin persistencia que permita demostrar el contrato RBAC antes de que existan los endpoints de negocio de HU-05+.
- Respuestas **401 `UNAUTHENTICATED`** y **403 `FORBIDDEN`** en formato D3.1.
- Feature tests de Pest para el esquema, 401, 403, acceso del productor e inventario de rutas (`TS-15`, `ts-04.02`).

**Fuera / diferido (con motivo):**
- `production_access` → diferida por la decisión aprobada en `TS-54` hasta que exista `productions`; no se crea ni se testea en esta HU.
- Los endpoints de escritura reales de artistas/producciones → sus HU (HU-05+). Aquí se usa un endpoint técnico para ejercitar la autorización, sin crear un contrato de negocio prematuro.
- Migraciones de `productions`, `songs`, `versions`, `comments`, `studio_sessions` → vetadas por «Qué NO hacer todavía» del `CLAUDE.md`.
- Provisión JIT de usuarios y vinculación de `artists.user_id` → flujo de invitación/onboarding de HU-05+. TS-15 no consulta ni crea usuarios locales durante la autenticación.
- Hash de integridad y S3 → fuera del alcance del Sprint 1 (`CLAUDE.md` raíz §5).

## 2. Dependencias

- **ADR (DECIDIDO):** `D3.1` (formato de error + manejador centralizado), `D4.8` (RBAC por claim de Auth0), `D4.1` (Form Requests), `D4.2` (API Resources por rol), `D4.4` (capas), `D6.1/D6.6/D6.7` (UUID, nombres, índices).
- **Seguridad previa:** `TS-51` dejó el manejador D3.1 y el backend de `TS-14` ya integró la validación del JWT, el claim de rol y `/me`. El rol llega desde `UserRepositoryContract::fromAccessToken()` como enum `Role`; la autorización lee ese valor, no una columna local.
- **Modelo aprobado:** `TS-54`, integrado en `develop` mediante `e5ec712`, define el contrato exacto de `users` y `artists` en [`../../erd/modelo-minimo-sprint-1.md`](../../erd/modelo-minimo-sprint-1.md).
- **Trabajo paralelo de HU-03:** el equipo conserva `TS-14` abierto para completar sus pendientes. TS-15 reutiliza solamente el contrato backend ya integrado; no modifica ni reconcilia el resto de HU-03.
- **Externa:** el claim namespaced `https://trackstudio.site/roles` ya fue verificado con un token real en `TS-14` (`ts-03.10`).

## 3. Contrato técnico

### 3.1 Persistencia mínima (`TS-15`, `ts-04.03`)

Las migraciones implementan literalmente el modelo aprobado en `TS-54`; esta spec no abre una segunda fuente de verdad para columnas o relaciones:

- `users`: UUID como PK, `auth0_sub` obligatorio y único, `email` **nullable y único**, timestamps con zona horaria. No contiene `role`, `name`, `password` ni `remember_token`.
- `artists`: UUID como PK; datos, estados, vínculos, restricciones e índices definidos en el ERD aprobado. Las FKs no usan borrado en cascada.
- Se elimina la tabla `password_reset_tokens` heredada del esqueleto de Laravel.
- No existe `production_access` en esta entrega.

El rol se obtiene exclusivamente del JWT (D4.8). La base local no participa en la decisión de autorización y el endpoint `/api/v1/me` conserva su propiedad comprobada de **cero consultas SQL**.

### 3.2 Endpoint técnico y autorización

`POST /api/v1/rbac-check` no recibe cuerpo, no escribe en base de datos y responde **204 No Content** cuando la autorización prospera. Es una sonda temporal de aceptación de RNF-01, no un endpoint de dominio.

La ruta aplica, en este orden:

1. `auth:auth0-api`, para validar el JWT y construir el usuario stateless.
2. La ability `perform-producer-action`, respaldada por una Policy/Gate que autoriza únicamente `Role::Productor`.

No se necesita Form Request ni API Resource porque no existe entrada ni representación de salida. Los futuros endpoints de negocio sí respetarán el flujo completo D4.4 y sus contratos propios.

### 3.3 Errores (D3.1)

La forma de error la construye el manejador centralizado existente en `bootstrap/app.php`; esta HU no la redefine ni formatea errores en controladores. El contrato completo vive en [`HU-03.md`](HU-03.md) §3.1.

- Sin token → **401**, `code: UNAUTHENTICATED`.
- Con rol `artista` → **403**, `code: FORBIDDEN`.
- Con rol `productor` → **204**, sin cuerpo.
- En producción (`app.debug=false`) nunca se expone `getMessage()` de un 500.

El `AuthenticationException` ya queda traducido a D3.1 por la configuración de excepciones integrada en `TS-51/TS-14`; no se agrega un método `unauthenticated()` paralelo.

### 3.4 Cobertura de rutas

«100 % de rutas protegidas» significa que toda ruta de negocio que modifique o exponga recursos restringidos debe tener autenticación **y** autorización explícitas. El inventario actual queda clasificado así:

| Ruta | Clasificación | Middleware exigido |
|---|---|---|
| `GET /api/v1/health` | Pública por diseño | Ninguno |
| `GET /api/v1/me` | Identidad del propio token; accesible a ambos roles | `auth:auth0-api` |
| `POST /api/v1/rbac-check` | Acción reservada a productor | `auth:auth0-api` + `can:perform-producer-action` |

El test de inventario debe fallar si una ruta nueva bajo `/api/v1` queda sin clasificar o si la sonda pierde alguno de sus dos controles.

## 5. Notas de implementación (para el humano)

- Antes de escribir la Policy, usar `graphify explain "policy"` / `graphify query "middleware auth"` si el índice del repositorio está disponible; si no lo está, registrar la limitación y buscar con `rg`.
- La fuente de verdad del rol es el claim del JWT. No se agrega `users.role`, ni siquiera para presentación.
- El namespace del claim se lee de una sola clave de configuración (`config('auth0.roles_claim')`), idéntica en Auth0 y el backend.
- La autenticación sigue siendo stateless: ni el guard, ni `/me`, ni la sonda RBAC hacen provisión JIT o consultas a `users`.
- Los tests de esquema pueden crear filas locales con factories/fixtures sin conectar esas filas al usuario stateless usado por los tests RBAC.
- El orden de trabajo respeta C1–C3: aprobar esta spec → escribir tests rojos → comprobar mutaciones → entregar al humano las instrucciones de implementación.

## 6. Decisión sobre sesiones server-side

La migración inicial actual también crea `sessions`, mientras el backend funciona como API stateless y el modelo aprobado en `TS-54` solo define `users` y `artists`. Se propone:

- eliminar `sessions` de esa migración;
- usar `SESSION_DRIVER=array` en el entorno de referencia mientras no exista una necesidad aprobada de sesión de servidor.

Esto evita conservar una tercera tabla sin contrato y hace coherente la configuración de referencia con Auth0 stateless. La decisión queda aprobada el 2026-10-01 mientras la API conserve este modelo. Si en el futuro deja de ser stateless, reintroducir persistencia de sesiones requiere una decisión y contrato nuevos; no se activa implícitamente.
