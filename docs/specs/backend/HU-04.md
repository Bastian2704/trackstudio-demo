# HU-04 (backend) — RBAC y el 403

> **Jira:** `TS-15` · **Sprint:** 1 · **Cubre:** RF-01 (parcial, acceso), **RNF-01** (control de acceso)
> **Contraparte:** [`../frontend/HU-04.md`](../frontend/HU-04.md)
> **Estado:** `[x]` borrador · `[ ]` aprobada · `[ ]` implementada

Este 403 es la **primera evidencia auditable de RNF-01** para la Sprint Review. La meta a nivel de historia (un `artista` recibe 403 al escribir; sin token → 401; un test por caso) vive en Jira; aquí va el contrato de backend y sus tests.

## 1. Alcance en esta capa

**Dentro:**
- Migraciones del modelo mínimo aprobado en `TS-54`: `users`, `artists` y, solo si allí se aprueba, `production_access`. Ninguna otra tabla.
- Una **Policy** que el rol `artista` no puede satisfacer sobre un endpoint de escritura de prueba (`TS-15`, `ts-04.03`).
- Respuestas **401 `UNAUTHENTICATED`** y **403 `FORBIDDEN`** en formato D3.1.
- Feature tests de Pest para 401, 403 y 2xx del productor (`TS-15`, `ts-04.02`).

**Fuera / diferido (con motivo):**
- El endpoint de escritura real de artistas/producciones → sus HU (HU-05+). Aquí basta un endpoint de escritura **de prueba** para ejercitar la Policy.
- Migraciones de `productions`, `songs`, `versions`, `comments`, `studio_sessions` → vetadas por "Qué NO hacer todavía" del `CLAUDE.md`. No se crean ni se testean.
- Hash de integridad y S3 → fuera del alcance del Sprint 1 (`CLAUDE.md` raíz §5). *(Nota 2026-09-17: el bloque 7 del ADR, que antes era el motivo del veto, está **cerrado** desde el 2026-08-18. El veto sigue, pero por alcance de sprint.)*

## 2. Dependencias

- **ADR (DECIDIDO):** `D3.1` (formato de error + manejador centralizado), `D4.8` (RBAC por claim de Auth0), `D4.1` (Form Requests), `D4.2` (API Resources por rol), `D4.4` (capas), `D6.1/D6.6/D6.7` (UUID, nombres, índices).
- **Tareas previas:** `TS-51` (manejador D3.1, ya cerrado) y `TS-14` (validación del JWT, rol y `/me`). El rol llega desde `UserRepositoryContract::fromAccessToken()`; la Policy lee `$user->role`, que es un `Role` enum, no un string.
- **Modelo previo:** `TS-54` aprueba `users`/`artists` y decide si `production_access` se difiere.
- **Externas:** el claim de rol namespaced (`https://trackstudio.site/roles`, D4.8) ya fue verificado dentro de un token real (`TS-14`, `ts-03.10`).

## 3. Contrato técnico

**Flujo de request (D3.1):** `Middleware(JWT/claim) → Form Request → Controller → Policy → Service → Eloquent/Contratos → API Resource → JSON`. Ningún controlador formatea errores a mano; todo error pasa por el manejador centralizado (`bootstrap/app.php → withExceptions`).

**Migraciones (`TS-15`, `ts-04.03`).** Solo las aprobadas en `TS-54`, con las convenciones del ADR:
- PK/FK en **UUID** (`HasUuids`, `foreignUuid()`) — D6.1.
- `auth0_sub` en `users`: **único e indexado** (es la clave de búsqueda por request — corrección registrada en el handoff de backend, omisión de D6.7).
- `production_access`: índice **único parcial** `(production_id, user_id) WHERE revoked_at IS NULL` — D6.7.
- Nombres: tablas plural `snake_case`, FKs `{singular}_id`, booleanos `is_`/`has_` — D6.6.

**Endpoint de escritura de prueba.** Una ruta autenticada bajo `/api/v1/…` cuya Policy exige rol `productor`. Sirve solo para ejercitar RBAC; no es un endpoint de negocio final.

**Forma del error (D3.1).** La construye el manejador centralizado de **TS-51**; esta HU no la redefine, solo afirma dos casos sobre ella. La forma completa y sus tests están en [`HU-03.md`](HU-03.md) §3.1. *(Corregido 2026-09-17: esta spec decía "nivel pragmático mientras el `type` apunte a dominio no resuelto". La decisión `3.6` del ADR se cerró en **completo** —con `type` e `instance`— porque el dominio `trackstudio.site` ya está confirmado.)* El campo `code` en `SCREAMING_SNAKE_CASE` es el contrato estable con el frontend:
- Sin token → **401**, `code: UNAUTHENTICATED`. Requiere sobreescribir el `unauthenticated()` de Laravel para que el 401 emita este cuerpo (el 401 por defecto del SDK de Auth0 no tiene esta forma).
- `artista` sobre endpoint de `productor` → **403**, `code: FORBIDDEN`.
- En producción (`app.debug=false`) nunca se expone `getMessage()` de un 500.

**Salida (D4.2).** El usuario se devuelve vía API Resource, filtrando campos por rol.

## 4. Criterios de aceptación de esta capa → tests (Pest)

| # | Test (archivo::caso) | Qué afirma | Cómo se prueba que FALLA (C3) |
|---|---|---|---|
| 1 | `tests/Feature/RbacTest.php::sin token responde 401 UNAUTHENTICATED` | Petición sin `Authorization` al endpoint de prueba → status 401 **y** cuerpo con `code === "UNAUTHENTICATED"` (no solo el status). | Quitar la sobreescritura de `unauthenticated()`: el status sigue 401 pero el `code` desaparece → el test debe ponerse rojo por el cuerpo. |
| 2 | `tests/Feature/RbacTest.php::artista recibe 403 FORBIDDEN al escribir` | Token con rol `artista` → 403 **y** `code === "FORBIDDEN"`. | Cambiar la Policy para que devuelva `true`: el 403 pasa a 2xx → rojo. |
| 3 | `tests/Feature/RbacTest.php::productor sí puede escribir` | Token con rol `productor` → 2xx. Ancla el 403 (prueba que no se rechaza a todos). | Endurecer la Policy para negar también a `productor` → rojo. |
| 4 | `tests/Feature/ErrorShapeTest.php::el error respeta el contrato D3.1` | El JSON de error tiene la **forma** de D3.1 (campos y `code` en SCREAMING_SNAKE_CASE), no solo el status. | Formatear un error a mano fuera del manejador central → la forma cambia → rojo. |

> Los tests afirman la **forma del JSON**, no solo el código de estado. Un test que solo mira `status === 403` pasa aunque el cuerpo esté mal — exactamente el tipo de test que no puede fallar que la metodología prohíbe.

## 5. Notas de implementación (para el humano)

- Antes de escribir la Policy, `graphify explain "policy"` / `graphify query "middleware auth"` para reutilizar lo que `TS-51` y `TS-14` dejaron, no reescribirlo.
- La fuente de verdad del rol es el **claim del JWT** (D4.8), no una columna. Si conservas `users.role`, es solo para display, nunca para autorizar.
- El namespace del claim se lee de **una sola** clave de config (`config('auth0.roles_claim')` desde `.env`), idéntica en la Action de Auth0, el middleware y el frontend.
- **Heredado de HU-03 (`ts-03.11`, 2026-09-30):** la migración de `users` de `ts-04.03` reemplaza la del esqueleto de Laravel. La tabla identifica al usuario por `auth0_sub` y **no** lleva `password` ni `remember_token`; desaparecen también `password_reset_tokens` y el `password` de `App\Models\User`. Sin esto no se cumple "el backend solo persiste `auth0_sub`". Ver [`HU-03.md`](HU-03.md) §3.5.
- **Heredado de HU-03 (`TS-14`, `ts-03.11`):** la migración de `users` reemplaza la del esqueleto de Laravel. La tabla identifica al usuario por `auth0_sub` y no lleva `password` ni `remember_token`; desaparecen también `password_reset_tokens` y el `password` de `App\Models\User`.
- Provisión JIT del usuario local: define cómo el endpoint resuelve un `users` local desde el `sub` del token cuando aún no hay registro (crear-si-no-existe o seed de prueba). Documenta la elección aquí en §6.
