## 1. Alcance en esta capa

Un endpoint de solo lectura que devuelve, en una sola respuesta, los conteos y la actividad reciente del estudio, calculados con las tablas existentes.

**Dentro:**

- `GET /api/v1/dashboard`, solo para el productor.
- Artistas por estado, producciones por formato, canciones por estado, canciones sin versión verificada, versiones verificadas (cantidad, bytes y duración totales) y las 5 versiones verificadas más recientes.

**Fuera / diferido (con motivo):**

- Comentarios y sesiones → sus tablas llegan en S5/S6 (`CLAUDE.md` §5).
- Porcentaje de avance, portada y demás métricas del marco `1:76` → sin RF ni datos (roadmap, «Reglas de alcance»).
- Dashboard del artista → `production_access` sigue vetada hasta HU-20/HU-21.
- Filtros por fecha o por artista, caché y paginación → nadie los pidió. Se añaden si el volumen lo exige.
- Versiones `fallida` o `pendiente` como métrica → ruido operativo; solo cuentan las `verificada`.
- `/me` (`MeController`) → no cambia.

## 3. Contrato técnico

### 3.1 Ruta y autorización

```
GET /api/v1/dashboard
middleware: auth:auth0-api, can:perform-producer-action
```

Reutiliza la Gate `perform-producer-action` (`RbacPolicy`, ya registrada en `AppServiceProvider`). No hace falta Policy nueva porque no hay modelo propio. Sin token → 401 `UNAUTHENTICATED`; rol artista o sin rol → 403 `FORBIDDEN`, ambos por el manejador central (D3.1).

Sin parámetros de consulta y sin Form Request: no hay entrada que validar.

### 3.2 Capas (D4.4)

`DashboardController` (invocable) → `DashboardService::summary()` → `DashboardResource` → JSON.

- El Service lanza consultas agregadas (`groupBy` + `count`/`sum`), no carga colecciones para contarlas en PHP.
- **Número de consultas constante:** no crece con la cantidad de datos (test 9). Las relaciones de `recent_versions` van con eager loading.

### 3.3 Respuesta 200

```json
{
  "data": {
    "artists": {
      "total": 3,
      "by_status": { "invitado": 1, "activo": 1, "inactivo": 1 }
    },
    "productions": {
      "total": 2,
      "by_format": { "sencillo": 1, "ep": 1, "album": 0 }
    },
    "songs": {
      "total": 4,
      "by_status": { "por_hacer": 2, "en_progreso": 1, "finalizada": 1 },
      "without_verified_version": 2
    },
    "versions": {
      "verified": 5,
      "total_size_bytes": 734003200,
      "total_duration_ms": 912000
    },
    "recent_versions": [
      {
        "id": "uuid",
        "version_number": 3,
        "label": "Mezcla final",
        "verified_at": "2026-11-12T15:04:05+00:00",
        "song": { "id": "uuid", "name": "Nombre de la canción" },
        "production": { "id": "uuid", "name": "Nombre de la producción" }
      }
    ]
  }
}
```

Reglas:

1. **Vigentes solamente.** Todo conteo y listado excluye las filas con `deleted_at` (el scope de `SoftDeletes`). La cascada de D4.5 (`ProductionService::deleteProduction`, `SongService::deleteSong`) garantiza que una versión vigente cuelga de una canción y una producción vigentes.
2. **Todas las claves siempre presentes.** `by_status` y `by_format` llevan una clave por cada caso del enum (`ArtistStatus`, `ProductionFormat`, `SongStatus`), con su `->value` como clave y `0` si no hay filas. Las claves salen del enum, no de los datos.
3. **`total`** es la suma de su desglose.
4. **`without_verified_version`**: canciones vigentes sin ninguna versión vigente en `verificada`. Una canción con solo versiones `pendiente` o `fallida` cuenta.
5. **`versions`** cuenta solo versiones vigentes en `verificada`. Una `verificada` siempre tiene `duration_ms` (CHECK `versions_verified_complete_check` de HU-13/HU-14), así que la suma no ve nulos.
6. **Enteros, no cadenas.** PostgreSQL devuelve `SUM` de `bigint` como `numeric` y PDO lo entrega como cadena: el Service lo convierte a `int`. Sin filas, `0`, no `null`.
7. **`recent_versions`**: como mucho 5 versiones vigentes en `verificada`, por `verified_at` descendente y `id` descendente como desempate. `label` puede ser `null`; el «v{n}» lo pinta el frontend (como en HU-14). `verified_at` en ISO 8601 con offset (D3.2). No expone `s3_key`, `etag`, `uploaded_by` ni URLs.
8. **Sin datos:** todo en 0 y `recent_versions: []`.

## 5. Notas de implementación (para el equipo)

- **Rellenar las claves desde el enum:** `collect(ArtistStatus::cases())->mapWithKeys(fn ($c) => [$c->value => $conteos[$c->value] ?? 0])` sobre un `Artist::query()->selectRaw('status, count(*) as total')->groupBy('status')->pluck('total', 'status')`. Mismo patrón para formatos y estados de canción.
- **Cuidado con el cast del enum en `pluck`:** si el modelo castea `status` a enum, la clave del `pluck` puede llegar como objeto o como valor según la consulta. Con `selectRaw` + `toBase()` llega el valor crudo.
- **Canciones sin verificada:** `Song::query()->whereDoesntHave('versions', fn ($q) => $q->where('upload_status', UploadStatus::Verificada))->count()`. `whereDoesntHave` respeta el soft delete de `versions`.
- **Sumas:** `(int) Version::query()->where(...)->sum('size_bytes')`.
- **Recientes:** `Version::query()->where(...)->with('song.production')->orderByDesc('verified_at')->orderByDesc('id')->limit(5)->get()`. La relación `song.production` ya existe; comprobar con `graphify` antes de añadir nada.
- **Resource:** `DashboardResource` recibe el array del Service y formatea `verified_at` con `toIso8601String()`, como `VersionResource`.
- No tocar `MeController` ni su ruta.
