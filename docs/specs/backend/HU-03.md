## 3. Contrato técnico

Flujo de request de D4.8: `Middleware(JWT/claim) → Form Request → Controller → Policy → Service → Eloquent/Contratos → API Resource → JSON`. Estas tres tareas construyen el primer eslabón y el último.

### 3.1 Enrutado y forma del error

**Enrutado.** `withRouting(api: routes/api.php, apiPrefix: 'api/v1')` en `bootstrap/app.php`. El prefijo `api/v1` sale de 3.1; el SDK de Auth0 registra su guard sobre el grupo `api`, así que las rutas **deben** vivir en `routes/api.php` (requisito del propio SDK, no nuestro).

**Cuerpo del error.** El de **D3.1**, en su variante **completa de RFC 9457** (decisión 3.6, cerrada el 2026-09-17): todos los campos del ejemplo del ADR, incluidos `type` e `instance`.

**Media type.** Toda respuesta construida por este manejador usa `Content-Type: application/problem+json`. `code`, `trace_id` y `errors` son miembros de extensión del Problem Details; usar `application/json` entregaría el cuerpo correcto con un contrato HTTP incompleto.

| Campo      | Origen                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------ |
| `type`     | `https://trackstudio.site/errors/{code en kebab-case}` — derivado del `code`, no escrito a mano |
| `title`    | Frase en español por código (nomenclatura §1: texto de cara al usuario en español)          |
| `status`   | El HTTP de la respuesta; siempre coincide con él                                            |
| `code`     | El del catálogo de D3.1, en `SCREAMING_SNAKE_CASE`                                          |
| `detail`   | Mensaje concreto del caso; en 500 con `app.debug=false`, **nunca** el `getMessage()` real    |
| `instance` | La ruta pedida (`$request->getPathInfo()`)                                                  |
| `errors`   | **Solo en 422**; forma nativa de Laravel (`campo → [mensajes]`)                             |
| `trace_id` | ULID generado por el backend en cada respuesta de error (decisión 3.7, ver abajo)           |

> **Drift del ADR, ya corregido (2026-09-17):** el ejemplo de D3.1 usaba `https://trackstudio.app/errors/validation`, resto de antes de comprar el dominio. Ahora dice **`trackstudio.site`**, el mismo del namespace del claim de D4.8. Se anota aquí porque el test 2 de §4 afirma el dominio: si alguien lo revierte, se pone rojo.

**Decisión 3.7 — origen del `trace_id`:** lo genera el **backend** como ULID (`Str::ulid()`, nativo de Laravel) cuando construye la respuesta de error. Si más adelante el frontend manda `X-Trace-Id`, el manejador lo respeta y solo genera cuando falta — un cambio de una línea en un solo sitio. Los tests de §4 afirman **presencia y forma** del `trace_id`, no su origen, así que no bloquean esa evolución.

**Catálogo como enum** (D4.6). Un `enum ErrorCode: string` que conoce su `status`, su `title` y deriva su `type`.

> **Excepción de nomenclatura, deliberada:** D4.6 y `nomenclatura.md` §6 piden el valor backed en minúscula/`snake_case`. Aquí el valor backed **es** el `code` del contrato con el frontend, que D3.1 fija en `SCREAMING_SNAKE_CASE`. Manda D3.1: el valor sale por el cable. Los **casos** del enum siguen en `PascalCase` (`case ResourceNotFound = 'RESOURCE_NOT_FOUND';`).

**Mapeo excepción → código.** Lo que el manejador cablea en esta tarea:

| Excepción                                              | HTTP | `code`                |
| ------------------------------------------------------ | ---- | --------------------- |
| `ValidationException`                                  | 422  | `VALIDATION_ERROR`    |
| `AuthenticationException`                              | 401  | `UNAUTHENTICATED`     |
| `AuthorizationException` · `AccessDeniedHttpException` | 403  | `FORBIDDEN`           |
| `NotFoundHttpException` · `ModelNotFoundException`     | 404  | `RESOURCE_NOT_FOUND`  |
| `ThrottleRequestsException`                            | 429  | `RATE_LIMITED`        |
| Cualquier otra                                         | 500  | `INTERNAL_ERROR`      |

**Regla de seguridad (D3.1).** Con `app.debug=false`, el `detail` de un 500 es un texto genérico fijo; el mensaje real **debe ir** al log/Sentry ligado al `trace_id`. Con `app.debug=true` sí puede exponerse — es lo que hace útil el entorno local, y lo que hace que el test 5 de §4 pueda ponerse rojo.

**Correlación con Sentry.** Para un error inesperado de API que termina en `500 INTERNAL_ERROR`, el mismo ULID aparece en dos sitios: `trace_id` en la respuesta y el tag buscable `trace_id` del evento de Sentry. El identificador interno del evento de Sentry y su trace de performance son conceptos distintos y **no sustituyen** este ULID del contrato.

El orden importa porque Laravel reporta la excepción antes de renderizarla. Un único resolvedor por request obtiene o genera el ULID y lo guarda como atributo del objeto `Request`; tanto el callback de reporte como el constructor del Problem Details consumen ese resolvedor. Antes de registrar `Sentry\Laravel\Integration::handles($exceptions)`, el callback de reporte añade el ULID al scope actual de Sentry. La integración oficial captura después la excepción exactamente una vez. No se llama además a `captureException()`, porque combinar ambos caminos duplicaría el evento.

Los errores que Laravel considera no reportables por defecto —por ejemplo 401, 403, 404 y validación— mantienen su `trace_id` en la respuesta, pero no se fuerzan hacia Sentry. La finalidad aquí es correlacionar fallos inesperados del servidor y no convertir errores esperados del cliente en ruido observacional.

**Configuración y secretos.** `.env.example` incorpora `SENTRY_LARAVEL_DSN=` vacío. El DSN real vive únicamente en variables de entorno de cada ambiente (D2.2/D8.4). No se habilita performance tracing ni envío de PII como parte del manejador de errores; D9.3 exige reporte de errores, no ampliar la recolección de datos. Una ausencia de DSN desactiva el envío, pero nunca cambia la respuesta HTTP ni provoca un segundo error.

### 3.2 Validación del JWT y extracción del rol

**Quién valida el JWT: el SDK, no nosotros.** Firma, JWKS, `iss`, `aud` y expiración los resuelve `auth0/login` v7 a través de su guard `auth0-api` (driver `auth0.authorizer`), aplicado con el middleware `auth:auth0-api` de Laravel. Escribir esa validación a mano es el error que el handoff de backend §8.3 marca explícitamente.

> **Decisión de diseño — aprobada el 2026-09-17.** El sprint doc del tablero anterior y D4.8 dicen "un middleware valida el JWT y extrae el claim". La primera mitad ya la cumple el guard del SDK. Para la segunda, **no hace falta una clase de middleware propia**: el punto de extensión que el SDK expone para esto es `UserRepositoryContract::fromAccessToken(array $user)`, que recibe los claims ya validados. Poner ahí la lectura del rol lo hace imposible de saltar (todo request autenticado pasa por él), mientras que un middleware aparte hay que acordarse de registrar en cada ruta. Se cumple D4.8 con el guard + el repositorio, y **no** se escribe una clase `Middleware` que solo reenvíe. D4.8 quedó reescrito en el ADR para decir esto mismo, así que el documento y el código no divergen. **Consecuencia para la trazabilidad:** la casilla `ts-03.03` de TS-14 habla de "middleware JWT": describe el efecto, no el artefacto; el artefacto es `App\Auth\UserRepository`. Anotarlo en el PR para que el tribunal no busque una clase que no existe.

**Qué se escribe para el guard:**

- `App\Auth\UserRepository implements Auth0\Laravel\UserRepositoryContract` — `fromAccessToken(array $user)` construye el usuario del request y le adjunta el rol leído del claim. `fromSession()` no aplica (arquitectura SPA + API, guard stateless; el handoff §8.2 descarta el flujo de sesión) y lanza/devuelve nulo explícitamente en vez de quedarse vacío por accidente.
- `enum Role: string` (D4.6) con exactamente dos casos: `case Productor = 'productor';` y `case Artista = 'artista';`. Los **valores** son los de Auth0 (D4.8) y están en español a propósito: son datos, no identificadores (nomenclatura §1).
- **Una sola clave de config** para el namespace: `config('auth0.roles_claim')`, alimentada por `AUTH0_ROLES_CLAIM` en `.env`. Es el punto que el handoff §8.8 exige centralizar, porque el mismo literal vive en la Action de Auth0 y en `VITE_AUTH0_ROLE_CLAIM` del frontend. **Ningún otro archivo del backend escribe ese literal**, y hay un test que lo prueba (§4, test 12).
- `config/auth.php`: el guard `auth0-api` apuntando al provider con este repositorio. `.env.example` con las claves `AUTH0_*` **sin valores reales** (D2.2, repo público).

**Contrato del claim.** El claim llega como **array de strings** (`"https://trackstudio.site/roles": ["artista"]`), que es la forma que produce la Action de Auth0. Se toma el primer valor; si el claim falta o viene vacío, el rol es `null` y **no se lanza excepción**: un token válido sin rol es un usuario autenticado sin permisos, es decir 401 no, 403 sí — y ese 403 lo decide la Policy de HU-04, no este código. Un valor que no corresponda a ningún caso del enum se trata igual que ausente (rol `null`), nunca se propaga como string crudo.

### 3.3 Respuesta 401 (guard × manejador de errores)

Sin token, o con token inválido, la petición a una ruta con `auth:auth0-api` termina en **401 con el cuerpo de D3.1 y `code: UNAUTHENTICATED`**. Esto **no** es gratis: hay que sobreescribir el `unauthenticated()` de Laravel / mapear la excepción en el manejador de §3.1, porque el 401 que emite el SDK por defecto no tiene esta forma (handoff §8.4). Es el punto de encuentro de las dos piezas y donde el `code` deja de ser una promesa del documento para ser una aserción de test.

**Qué cuenta como token inválido** (enmienda 2026-09-30). Los cuatro rechazos que hace el SDK terminan en el **mismo** 401: firma que no verifica contra el JWKS del tenant, `exp` vencido, `aud` que no contiene nuestro audience, e `iss` que no es nuestro tenant. El cuerpo no distingue el motivo: `code` es siempre `UNAUTHENTICATED` y el `detail` es el mismo texto genérico, para no decirle a quien prueba tokens cuál de las comprobaciones falló. El algoritmo esperado es **RS256**, el que emite el tenant (verificado en `ts-03.10`).

### 3.4 `GET /api/v1/me`

- **Ruta:** `GET /api/v1/me`, middleware `auth:auth0-api`. Controller delgado (D4.4) → `UserResource` (D4.2). Sin Service: no hay lógica de negocio que orquestar, y un Service que solo reenvía es la abstracción de un solo uso que el review caza (metodología §5).
- **Fuente de los datos: el token, no la base de datos.** Es deliberado y acotado a Sprint 1: la tabla `users` nace en HU-04 (`ts-04.03`). Este endpoint prueba que la cadena *token → claim → rol → JSON* funciona end-to-end; conectarlo a una fila local es trabajo de HU-04, y se anota en §6 cuando ocurra.
- **Forma de la respuesta (200):**

```json
{ "data": { "sub": "auth0|…", "role": "productor" } }
```

> **Corregido el 2026-09-17 al escribir los tests.** Esta spec pedía además `name` y `email`. Un **access token** de Auth0 no los lleva: son claims del *ID token*. Traerlos exigiría o bien inyectarlos como claims custom en la Action post-login (trabajo de infraestructura, fuera de esta spec), o bien llamar a la Management API en cada request (una dependencia de red y un límite de tasa dentro de un endpoint de humo). Y no hacen falta: el SPA ya tiene nombre y correo del ID token vía `useAuth0().user`. El endpoint prueba la cadena *token → claim → rol*, que es su razón de ser. **Si se quieren de todas formas**, es una línea en la Action de Auth0 más actualizar esta spec y el test 16 — en ese orden.

- **El Resource filtra (D4.2).** Solo esos dos campos salen. Los claims de infraestructura del token (`iss`, `aud`, `exp`, `iat`, `azp`, `scope`, y `email` si algún día llega) **no** se devuelven: no le sirven al cliente y describen la configuración interna de auth. Hay un test que lo afirma (§4, test 17).
- `role` sale como el **valor** del enum (`"productor"` / `"artista"`) o `null` si el token no trae claim. Ese string es el mismo contrato que ya consume `useRole.ts` en el frontend.

### 3.5 Sin credenciales propias (`ts-03.11`, enmienda 2026-09-30)

El criterio de la historia es "credenciales nunca almacenadas en el sistema propio". En esta HU se cumple por tres vías:

- **No se persiste nada.** Ni el guard ni `/api/v1/me` escriben o leen la base de datos (§3.4): el token se valida, se usa y se descarta con el request. No se guarda en caché, sesión ni tabla. Hay un test que lo afirma (§4, test 25).
- **El token no sale hacia los logs ni hacia Sentry.** Ningún código nuestro registra el token, la cabecera `Authorization` ni los claims completos. El único camino por el que podría filtrarse es el reporte de una excepción: por eso `send_default_pii` de Sentry se queda en `false` (ya fijado en §3.1), que es lo que hace que el SDK omita las cabeceras sensibles del request. Hay un test que lo afirma (§4, test 26).
- **Las claves `AUTH0_*` de `.env.example` van sin valores** (§3.2, D2.2).

> **Lo que esta HU no puede cerrar, y a quién le toca.** La casilla dice "el backend solo persiste `auth0_sub`". Hoy el esqueleto de Laravel trae una migración `create_users_table` con columna `password` y tabla `password_reset_tokens`, y `App\Models\User` declara `password` como asignable. Nada de eso se usa, pero existe. Reemplazarlo por la tabla `users` real (con `auth0_sub`, sin `password`) es la migración de `ts-04.03` (`TS-15`), y el veto de "Qué NO hacer todavía" no deja adelantarla aquí. **Consecuencia:** `ts-03.11` se puede marcar en lo que toca a tokens y logs al cerrar `ts-03.04`; la mitad de "solo `auth0_sub`" queda anotada como pendiente de `ts-04.03` en [`HU-04.md`](HU-04.md). **Reparto aprobado el 2026-09-30** y reflejado en las casillas `ts-03.11` (TS-14) y `ts-04.03` (TS-15) de Jira.

## 4. Criterios de aceptación de esta capa → tests

> **Reescrita el 2026-09-17**, después de ver los tests en rojo. La numeración original (1-19) se conserva para poder seguir el historial; qué cambió y por qué está en §6.

Pest (D4.7). **Los tests afirman la forma del JSON, no solo el status** — uno que solo mira `status === 401` pasa aunque el cuerpo esté mal, que es el tipo de test que la metodología prohíbe. Los códigos se afirman con **literales**, nunca importando el enum `ErrorCode`: si el test leyera el valor del mismo sitio que el código, un valor mal escrito quedaría verde y rompería el contrato con el frontend en silencio.

**Helpers compartidos** en `tests/Pest.php`: `impersonarToken(array $claims)` y `claimsDeToken(?string $rol, array $extra)` para saltarse el guard; `claimsDeTokenFirmado()`, `firmarJwt()`, `configurarSdkDePrueba()` y `registrarRutaProtegida()` para atravesarlo. `claimsDeToken()` **lee el namespace de `config('auth0.roles_claim')`** en vez de escribirlo literal: un test que copia el literal deja de detectar que el código lo tiene incrustado.

**Sobre la frontera externa (C4)** — reescrito el 2026-09-30. `impersonarToken()` se salta la verificación criptográfica del SDK: sirve para probar lo que hacemos **después** de validar (rol, Resource), y por eso lo siguen usando los tests de `/me`. Pero la verificación no es solo del SDK: que rechace una `aud` ajena depende de **nuestra** configuración (`AUTH0_*`, guard, mapeo del 401), y un audience mal puesto dejaría toda la suite verde. Eso lo cubren los tests 20-23b, que pasan por el guard real con JWT firmados por una clave de prueba, y el test 24, que usa un access token real del tenant.

## 5. Notas de implementación (para el humano)

**Orden.** El manejador de errores completo y en verde antes de tocar Auth0 (ya cumplido). Es la única de las tres piezas que no depende de nada externo, y las otras dos se apoyan en su forma de error.

**Manejador de errores:**

- El `withExceptions` ya tiene el `shouldRenderJsonWhen` del esqueleto: se conserva, es justo la condición del test 10.
- La derivación `type` ← `code` se escribe **una vez** dentro del enum (`str_replace('_', '-', strtolower($this->value))` o equivalente). En la versión instalada, `Str::kebab()` conserva los guiones bajos de un valor `SCREAMING_SNAKE_CASE`, por lo que no satisface este contrato. Si la derivación aparece en dos sitios, es el drift de §0 de la metodología esperando a ocurrir.
- El `detail` genérico del 500 también es texto de cara al usuario: en español.
- Instalar `sentry/sentry-laravel:^4.28` dentro de Sail. Registrar una sola vez `Sentry\Laravel\Integration::handles($exceptions)`, que es la API oficial para Laravel 11+; no combinarla con una captura manual de la misma excepción.
- El resolvedor del `trace_id` vive una sola vez en `bootstrap/app.php`: reutiliza el atributo del `Request` si ya existe y genera `Str::ulid()` solo cuando falta. El callback reportable se registra **antes** de `Integration::handles()` para añadir el tag al scope antes de que el SDK prepare el evento; el renderer reutiliza después ese mismo valor.
- El test 4b reemplaza la red por una implementación en memoria de `Sentry\Transport\TransportInterface`, conectada a un cliente real del SDK. Así se inspecciona el `Sentry\Event` final y no solo que se llamó a un mock. La comprobación de infraestructura se separa: en staging, `sentry:test` valida DSN/transporte; ninguna credencial entra a la suite ni al repo.
- Añadir `SENTRY_LARAVEL_DSN=` vacío a `.env.example`. No usar `sentry:publish --dsn=…` como mecanismo de cambios versionados: ese comando escribe el secreto en el `.env` local y puede enviar un evento de prueba.

**Guard JWT y rol:**

- `sail composer require auth0/login:^7` y `sail artisan vendor:publish --tag auth0`. Recuerda que `config.platform.php` en `composer.json` está pinneado a `8.4.24`; si el contenedor subió de parche, Composer falla la resolución antes que nada (handoff §4.3).
