## 3. Contrato técnico

`GET /api/v1/health`: sin autenticación y sin middleware adicional. Se invoca con un controlador invocable.

| Estado | HTTP | Cuerpo |
| --- | --- | --- |
| BD responde a `SELECT 1` | 200 | `{"status":"ok","checks":{"database":true},"timestamp":"…"}` |
| BD falla | 503 | `{"status":"degraded","checks":{"database":false},"timestamp":"…"}` |

- `Content-Type: application/json`. **Exento de D3.1** (ver D9.3): es un reporte de estado, no un error.
- Las claves son **exactamente** `status`, `checks` y `timestamp`, en los dos estados. No se envía `environment`, porque el repo es público y la ruta no pide autenticación.
- El fallo se **reporta** (`report($e)`), no solo se loguea. Así llega a Sentry con el `trace_id` que ya etiqueta el `reportable` de `bootstrap/app.php`. El mensaje nunca va al cuerpo.
- Keyword del monitor de UptimeRobot: `"status":"ok"`, con alerta si **no** aparece. Cubre tanto la caída total como el estado `degraded`.

## 5. Notas de implementación (para el humano)

- `HealthController.php` ya existe sin commitear. Hay que hacerle dos cambios:
  - Quitar la clave `environment` del cuerpo.
  - Sustituir `Log::error(...)` por `report($e)` y quitar el `use` de `Log`, que queda sin usar.
- En `routes/api.php`, registrar `Route::get('/health', HealthController::class)` **sin** `throttle`. El prefijo `api/v1` lo pone `bootstrap/app.php`.
- Los tests 5 a 8 simulan la caída con `DB::shouldReceive('select')`. Si el controlador usa otra API de `DB` (p. ej. `DB::connection()->getPdo()`), el mock no la intercepta. Mantener `DB::select('SELECT 1')`.
- `Exceptions::fake()` evita que `report()` intente enviar a Sentry durante los tests.
