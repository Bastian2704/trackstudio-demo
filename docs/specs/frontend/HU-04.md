# HU-04 (frontend) — RBAC en el cliente

> **Jira:** `TS-15` · **Sprint:** 1 · **Cubre:** RF-01 (parcial, acceso), **RNF-01** (control de acceso)
> **Contraparte:** [`../backend/HU-04.md`](../backend/HU-04.md)
> **Estado:** `[x]` borrador · `[ ]` aprobada · `[ ]` implementada

El backend emite 401/403 con la forma D3.1 (ver contraparte). Esta capa **reacciona** a ese contrato: protege rutas por rol y traduce el campo `code` a la pantalla correcta. La meta a nivel de historia vive en Jira.

## 1. Alcance en esta capa

**Dentro:**
- Rutas protegidas por rol; el rol viene del token de Auth0 (`TS-15`, `ts-04.06`).
- Interceptor de axios que reacciona al campo **`code`** de D3.1 (`UNAUTHENTICATED`, `FORBIDDEN`), **nunca al texto del mensaje**.
- Mapeo de `FORBIDDEN` a su pantalla; de `UNAUTHENTICATED` al flujo de login.

**Fuera / diferido (con motivo):**
- Las vistas de los módulos funcionales (artistas, producciones…) → sus HU. Aquí basta la pantalla mínima autenticada y la de "sin permiso".
- Vista restringida completa del artista → HU-21.

## 2. Dependencias

- **ADR (DECIDIDO):** `D5.1` (access token **en memoria** vía `@auth0/auth0-react`; nunca `localStorage`/`sessionStorage`; refresh tokens con rotación gestionados por el SDK), `D3.1` (el frontend consume el campo `code`).
- **Tareas previas:** `TS-14` (`Auth0Provider`, token en memoria, login/logout e interceptor). El endpoint de escritura de `TS-15` debe existir para la integración de ruta.
- **Externas:** app SPA en Auth0 con callbacks/web origins para `localhost` y staging (`TS-14`, `ts-03.10`). Namespace del claim idéntico al del backend (una sola config).

## 3. Contrato técnico

- **Estado de servidor:** TanStack Query. **Errores:** el interceptor de axios inspecciona `error.response.data.code` (contrato estable D3.1) y despacha por ahí; el texto del mensaje es para el humano, nunca para lógica.
- **Rutas protegidas:** un guard de ruta lee el rol del token (claim namespaced, misma clave de config que el backend) y decide render vs redirección. `artista` no ve ni alcanza rutas de `productor`.
- **Token en memoria (D5.1):** el access token nunca toca `localStorage`/`sessionStorage`. La continuidad de sesión es por refresh token con rotación del SDK. Esto debe quedar cubierto por `TS-15`, `ts-04.06`.

## 4. Criterios de aceptación de esta capa → tests (Vitest)

| # | Test (archivo::caso) | Qué afirma | Cómo se prueba que FALLA (C3) |
|---|---|---|---|
| 1 | `interceptor.test.ts::mapea code=FORBIDDEN a la pantalla sin-permiso` | Ante una respuesta `{ code: "FORBIDDEN" }`, el interceptor despacha a la pantalla de sin permiso. | Cambiar el interceptor para que despache según `error.message` en vez de `code` → con un mensaje distinto al esperado, deja de mapear → rojo. |
| 2 | `interceptor.test.ts::ignora el texto del mensaje` | Dos respuestas con el **mismo** `code` y **distinto** `message` producen el **mismo** despacho. | Hacer que el interceptor ramifique por `message` → los dos casos divergen → rojo. |
| 3 | `rutaProtegida.test.tsx::artista no accede a ruta de productor` | Con rol `artista`, la ruta de `productor` no renderiza su contenido (redirige o muestra sin-permiso). | Quitar la comprobación de rol del guard → el contenido aparece → rojo. |
| 4 | `token.test.ts::el token no está en localStorage/sessionStorage` | Tras autenticar, ni `localStorage` ni `sessionStorage` contienen el access token (D5.1). | Simular una implementación que persista el token en `localStorage` → rojo. |

> El test 2 es el que protege la decisión D3.1 de verdad: afirmar el mapeo por `code` sin comprobar que **ignora** el `message` deja la puerta abierta a acoplarse al texto.

## 5. Notas de implementación (para el humano)

- `graphify query "axios interceptor"` antes de modificarlo: `TS-14` ya dejó la base.
- El rol se lee del claim del token, con la **misma clave de config** que el backend (`roles_claim`). No hardcodees el namespace en dos sitios.
- La pantalla mínima autenticada consume `GET /api/v1/me` (`TS-14`) y muestra el rol; sobre ella se prueba el guard.
