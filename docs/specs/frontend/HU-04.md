# HU-04 (frontend) — RBAC en el cliente

> **Jira:** `TS-15` · **Sprint:** 1 · **Cubre:** RF-01 (parcial, acceso), **RNF-01** (control de acceso)
> **Contraparte:** [`../backend/HU-04.md`](../backend/HU-04.md)
> **Estado:** `[x]` borrador · `[x]` aprobada (2026-10-02) · `[x]` implementada (2026-10-02)

El backend emite 401/403 con la forma D3.1 (ver contraparte). Esta capa **reacciona** a ese contrato: protege rutas por rol y traduce el campo `code` a la pantalla correcta. La meta a nivel de historia vive en Jira.

## 1. Alcance en esta capa

**Dentro:**
- Rutas protegidas por rol; el rol viene del token de Auth0 (`TS-15`, `ts-04.06`).
- Interceptor de axios que reacciona al campo **`code`** de D3.1 (`UNAUTHENTICATED`, `FORBIDDEN`), **nunca al texto del mensaje**.
- Mapeo de `FORBIDDEN` a su pantalla; de `UNAUTHENTICATED` al flujo de login.
- Una ruta mínima `/productor`, sin UI de dominio, para demostrar que el rol `artista` no alcanza contenido reservado al productor.

**Fuera / diferido (con motivo):**
- Las vistas de los módulos funcionales (artistas, producciones…) → sus HU. Aquí basta la pantalla mínima autenticada y la de "sin permiso".
- Vista restringida completa del artista → HU-21.

## 2. Dependencias

- **ADR (DECIDIDO):** `D5.1` (access token **en memoria** vía `@auth0/auth0-react`; nunca `localStorage`/`sessionStorage`; refresh tokens con rotación gestionados por el SDK), `D3.1` (el frontend consume el campo `code`).
- **Tareas previas:** `TS-14` (`Auth0Provider`, token en memoria, login/logout e interceptor). El endpoint de escritura de `TS-15` debe existir para la integración de ruta.
- **Externas:** app SPA en Auth0 con callbacks/web origins para `localhost` y staging (`TS-14`, `ts-03.10`). Namespace del claim idéntico al del backend (una sola config).

## 3. Contrato técnico

### 3.1 Rol y rutas

`useRoles()` lee del usuario de Auth0 el claim cuyo **namespace** configura `VITE_AUTH0_ROLE_CLAIM`. Su valor debe coincidir con `AUTH0_ROLES_CLAIM` en el backend y con la Action de Auth0; las claves de entorno son propias de cada capa. Solo acepta los roles conocidos `productor` y `artista`. Un claim ausente, mal formado o con valores desconocidos produce una lista vacía y, por tanto, deniega el acceso a una ruta con roles permitidos.

La topología mínima queda así:

| Ruta | Acceso | Resultado |
|---|---|---|
| `/me` | Usuario autenticado con rol `productor` o `artista` | Pantalla de sesión de HU-03. |
| `/productor` | Usuario autenticado con rol `productor` | Contenido mínimo de humo: no crea una vista de dominio futura. |
| `/403` | Pública | Pantalla `Forbidden`. |

`RequireAuth` comprueba primero la sesión y `RequireRole` decide después por rol. Cuando el rol no está permitido, `RequireRole` reemplaza la navegación actual por `/403`; nunca renderiza el contenido hijo restringido.

### 3.2 Errores de la API

El interceptor de axios inspecciona `error.response.data.code` (contrato estable D3.1) y delega en handlers inyectados:

- `UNAUTHENTICATED` → reinicia el flujo de login mediante `loginWithRedirect()`;
- `FORBIDDEN` → navega a `/403` con reemplazo del historial;
- cualquier otro código, una respuesta sin cuerpo o un error de red → no dispara ninguno de esos handlers.

Después de aplicar el efecto correspondiente, el interceptor conserva el rechazo con el mismo error para que TanStack Query o el consumidor mantengan su estado de error. El campo `message` es diagnóstico para humanos y no interviene en ninguna rama.

### 3.3 Token en memoria (D5.1)

`Auth0Provider` se configura con `cacheLocation="memory"` y `useRefreshTokens`. El código de aplicación no escribe access tokens en `localStorage` ni `sessionStorage`. Vitest protege la configuración que gobierna al SDK; la comprobación posterior al login real en staging confirma la ausencia del token en ambos storages, porque el efecto interno del SDK no se sustituye por una simulación como evidencia C4.

### 3.4 Retorno a la ruta pedida tras el login

Con el token en memoria (§3.3), abrir una ruta protegida escribiendo su URL o recargando la página arranca sin sesión: `RequireAuth` lanza el login y Auth0 guarda la ruta pedida en `appState.returnTo`. Auth0 vuelve siempre a `redirect_uri` (la raíz). Al completar ese retorno, la aplicación **navega con el router** a `appState.returnTo` y, si falta, a `/`. Así se evalúan `RequireRole` y la pantalla pedida, no la redirección de `Home` a `/me`.

El `onRedirectCallback` por defecto del SDK no basta: solo hace `history.replaceState`, que `BrowserRouter` no observa. La aplicación sigue en `/` y `Home` la manda a `/me`, sea cual sea el rol. Detectado en staging durante `ts-04.09` el 2026-10-02: tanto el productor como el artista terminaban en `/me` al entrar a `/productor` por URL. Con navegación interna sin recarga, las dos pantallas eran las correctas.

### 3.5 Evidencia de integración

La evidencia del cliente y la del servidor son complementarias y no se confunden:

- en el frontend, el usuario `artista` visita `/productor`, termina en `/403` y nunca ve el contenido restringido; el usuario `productor` sí lo ve;
- contra `POST /api/v1/rbac-check`, sin token se observa 401 `UNAUTHENTICATED`, el token de `artista` obtiene 403 `FORBIDDEN` y el de `productor` obtiene 204;
- un 403 D3.1 simulado en Vitest demuestra que el interceptor usa `code` y que la aplicación lo cablea a la pantalla `/403`.

## 5. Notas de implementación (para el humano)

- El índice local de `graphify` no estaba disponible al reconciliar esta spec (`graphify-out/graph.json` ausente); se inspeccionaron los símbolos existentes con búsqueda dirigida. Reintentar `graphify query "axios interceptor RequireRole useRole"` si se regenera el índice.
- El rol se lee del claim del token. El **valor** del namespace debe coincidir en Auth0 y ambas capas; no se hardcodea dentro de los hooks o componentes.
- `/me` conserva el contrato de HU-03 para ambos roles. La demostración exclusiva del productor se hace en `/productor`, sin convertir `/me` en una ruta más restrictiva que el backend.
- El `onRedirectCallback` necesita el `navigate` de React Router, así que el `Auth0Provider` tiene que quedar **dentro** del `BrowserRouter`. El patrón habitual es un componente envoltorio que llama a `useNavigate()` y le pasa el callback al proveedor. La configuración de §3.3 no cambia (test 9).
- `App.tsx` registra `/productor` bajo `RequireAuth` y `RequireRole(['productor'])`; el handler `onForbidden` navega a `/403` reemplazando la entrada del historial.

**Deuda conocida** (review de la enmienda §3.4, 2026-10-02):

- `TS-57` — la mutación que quita `{ replace: true }` del `onRedirectCallback` **sobrevive**: ningún test comprueba que la entrada `/?code=…&state=…` se reemplaza en el historial. Impacto bajo: el botón "atrás" volvería a la URL del callback con un `code` ya consumido. Se cubre añadiendo una aserción al test 10.
- `TS-58` (prioridad baja) — el envoltorio `Auth0ProviderRouter` vive en `main.tsx`, y ESLint emite un warning `react-refresh/only-export-components` en `main.tsx:10`. No tiene impacto funcional. Si se mueve a su propio archivo, primero se actualiza esta nota.
