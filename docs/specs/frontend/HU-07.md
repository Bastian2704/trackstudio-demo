# HU-07 (frontend) — Cambiar el estado de un artista

> **Jira:** `TS-18` · **Sprint:** 2 · **Cubre:** RF-01 (estado del artista), RNF-01 (control de acceso)
> **Contraparte:** [`../backend/HU-07.md`](../backend/HU-07.md)
> **Estado:** `[x]` borrador · `[x]` aprobada (2026-10-12) · `[x]` implementada (2026-10-12)

Los criterios de aceptación de la historia viven en Jira. El contrato de la API (ruta, cuerpo, regla de reactivación, idempotencia y errores) vive en la spec backend y aquí solo se referencia. Esta spec define dónde se cambia el estado en la interfaz, sus textos, la confirmación y el manejo de errores.

## 1. Alcance en esta capa

**Dentro:**

- Una sección «Estado» en `ArtistEditPage` (`/artistas/:id/editar`), debajo del formulario, con el estado actual y un botón para desactivar o reactivar.
- Confirmación con `AlertDialog` **solo al desactivar** (decisión del equipo del 2026-10-12).
- Aviso de éxito, aviso de error y protección contra el doble envío.
- Invalidar el listado de artistas para que muestre el estado nuevo.

**Fuera / diferido (con motivo):**

- Botón en la fila del listado (`/artistas`) → descartado por decisión del equipo del 2026-10-12. El listado sigue mostrando el estado como hoy (HU-06).
- Que el artista vea su propio estado → HU-20/HU-21.
- La caché del listado tras **editar nombre o email** (HU-05) tiene el mismo retraso de `staleTime`. No se toca aquí: un cambio a la vez.

## 3. Contrato técnico

### 3.1 Ruta

Sin rutas nuevas. Todo ocurre en `/artistas/:id/editar`, que ya está protegida por `RequireAuth` y `RequireRole(['productor'])`. Un 401 o 403 de la API lo resuelve el interceptor de HU-04.

### 3.2 Pantalla y textos

Esta spec es la dueña de los textos de la interfaz de HU-07.

**Sección «Estado»**, debajo del formulario de edición. Se pinta solo cuando la precarga tiene datos, igual que el formulario.

| Elemento | Texto |
| --- | --- |
| Estado actual | «Estado: {etiqueta}», con la etiqueta de `STATUS_LABELS`: «Invitado», «Activo» o «Inactivo» |
| Botón si el estado es `invitado` o `activo` | «Desactivar artista» (variante `destructive`) |
| Botón si el estado es `inactivo` | «Reactivar artista» |
| Aviso de éxito (`role="status"`, el mismo de «Cambios guardados.») | «Artista desactivado.» · «Artista reactivado.» |
| Aviso de error (`role="alert"`) | «No se pudo cambiar el estado del artista. Inténtalo de nuevo.» |

**Diálogo al desactivar** (`role="alertdialog"`):

| Elemento | Texto |
| --- | --- |
| Título | «¿Desactivar artista?» |
| Descripción | «No podrás registrar producciones nuevas para este artista hasta reactivarlo.» |
| Botón de confirmar | «Desactivar» |
| Botón de cancelar | «Cancelar» |

- Cancelar cierra el diálogo sin petición.
- Tras el 200, el diálogo se cierra.
- Mientras la petición está en curso, el diálogo no se cierra: ni «Cancelar» ni Escape (mismo criterio que HU-08).
- Tras un error, el diálogo se cierra y el aviso de error queda en la página.
- **Reactivar no pide confirmación:** el clic envía la petición directamente.

### 3.3 Datos (TanStack Query + `api`)

- Nueva función `changeArtistStatus(id, active)` en `artistApi.ts`: `PUT /api/v1/artists/{id}/status` con cuerpo **exactamente** `{ active }`, y devuelve el `Artist` sin la envoltura `data`.
- El cliente **no calcula** el estado resultante. Reactivar puede devolver `invitado` o `activo` (backend §3.4), y la pantalla pinta lo que responde el servidor.
- `useMutation`. Con el 200:
  1. `setQueryData(['artists', id], artista)`: la etiqueta y el botón cambian sin volver a pedir el artista.
  2. Aviso de éxito según la acción enviada (`active: false` → «Artista desactivado.»; `true` → «Artista reactivado.»).
  3. `invalidateQueries({ queryKey: ['artists', 'list'] })`: el listado se vuelve a pedir la próxima vez que se monte, aunque esté dentro de su `staleTime` de 30 s. **No** se invalida el prefijo `['artists']`, porque eso volvería a pedir el artista que se acaba de guardar en la caché.
- **Envío en curso:** «Reactivar artista» y «Desactivar» del diálogo quedan deshabilitados; un segundo clic no genera otra petición.
- `STATUS_LABELS` pasa de `ArtistListPage.tsx` a `artistSchema.ts`, porque ahora tiene dos usos (mismo criterio que `FORMAT_LABELS` en HU-06).

### 3.4 Errores (por `code`, D3.1)

| Situación | Qué se muestra |
| --- | --- |
| Cualquier error al cambiar el estado (500, red, 404 si el artista se borró mientras tanto) | Se cierra el diálogo (si estaba abierto) y aparece el aviso de error de §3.2. El estado y el botón **no cambian**. |
| 422 | No se espera: el cliente siempre envía un booleano. Si llega, cae en la fila anterior. |
| 401 / 403 | Nada propio: los resuelve el interceptor de HU-04. |

- Ninguna rama mira `message`, `title` ni `detail`.

## 5. Notas de implementación (para el equipo)

- **Reutilizar:** el `AlertDialog` controlado de `ProductionEditPage` (`open`/`onOpenChange` con guarda de `isPending`, `onError` que lo cierra) y el `notice` que ya tiene `ArtistEditPage`.
- **Orden sugerido de Green:** mover `STATUS_LABELS` a `artistSchema.ts` → sección con etiqueta y botón (#1, #8) → `changeArtistStatus` + mutación + diálogo (#2, #3, #5) → reactivar (#4, #6) → errores (#7).
- **Una sola mutación** con `mutationFn: (active: boolean) => changeArtistStatus(id, active)`. En `onSuccess(artista, active)` tienes el booleano enviado para elegir el aviso.
- **Trampa:** no derives la etiqueta del `active` enviado. Pinta siempre `query.data.status`, que tras el `setQueryData` es lo que devolvió el servidor (test #4).
- **Trampa de `findBy…`** (handoff v23): mientras la consulta está pendiente se pinta «Cargando…» y no la sección. En los tests de error se espera primero a la señal del error.
