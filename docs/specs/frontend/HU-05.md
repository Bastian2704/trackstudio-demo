# HU-05 (frontend) — Registrar y editar artistas

> **Jira:** `TS-16` · **Sprint:** 2 · **Cubre:** RF-01 (alta y edición), RNF-01 (control de acceso)
> **Contraparte:** [`../backend/HU-05.md`](../backend/HU-05.md)
> **Estado:** `[x]` borrador · `[x]` aprobada (2026-10-06) · `[ ]` implementada

Los criterios de aceptación de la historia viven en Jira. El contrato de la API (rutas, `ArtistResource`, errores) vive en la spec backend y aquí solo se referencia. Esta spec define las pantallas, el formulario, sus estados y cómo se traduce cada respuesta a la interfaz.

## 1. Alcance en esta capa

**Dentro:**

- Dos rutas solo para el productor: alta (`/artistas/nuevo`) y edición (`/artistas/:id/editar`).
- Un formulario compartido con `name` y `email`, validación mínima en el cliente y mapeo del 422 a cada campo.
- Precarga del artista en la edición (`GET`), envío del alta (`POST`) y de la edición (`PUT`).
- Estados visibles: cargando, enviando, éxito, no encontrado y error.

**Fuera / diferido (con motivo):**

- Listado de artistas y navegación hacia estas pantallas → `TS-17` (HU-06). Hasta entonces se llega por URL.
- Cambio de estado → `TS-18` (HU-07). La pantalla no muestra ni edita `status`.
- Invitación del artista → HU-20 (S6).
- Borrado → ninguna HU de S2 lo pide.
- Mostrar fechas (`created_at`, `updated_at`) → no se pintan: la zona horaria de presentación sigue **ABIERTA** en D3.2.

## 3. Contrato técnico

### 3.1 Rutas

Se registran en `App.tsx` bajo `RequireAuth` y `RequireRole allowed={['productor']}`, igual que `/productor`.

| Ruta                   | Página             | Llamada a la API (backend §3.1)             |
| ---------------------- | ------------------ | ------------------------------------------- |
| `/artistas/nuevo`      | `ArtistCreatePage` | `POST /api/v1/artists`                      |
| `/artistas/:id/editar` | `ArtistEditPage`   | `GET` y `PUT /api/v1/artists/{id}`          |

- Los módulos son `src/routes/artists/ArtistCreatePage.tsx` y `src/routes/artists/ArtistEditPage.tsx`, con export default (`frontend/docs/nomenclatura.md` §3). Los tests los importan desde esas rutas.
- El cliente **no valida** que `:id` sea UUID: lo hace el backend, que responde 404 (§3.5).
- Un `artista` nunca ve estas pantallas: `RequireRole` lo manda a `/403`. Si aun así llegara un 403 de la API, lo resuelve el interceptor de HU-04; las páginas no lo tratan.

### 3.2 Pantallas y textos

Esta spec es la dueña de los textos de la interfaz de HU-05.

| Elemento                                          | Alta                  | Edición             |
| ------------------------------------------------- | --------------------- | ------------------- |
| Encabezado (`h1`)                                 | «Registrar artista»   | «Editar artista»    |
| Campos (con `label` asociado)                     | «Nombre», «Email»     | «Nombre», «Email»   |
| Botón de envío                                    | «Registrar»           | «Guardar cambios»   |
| Aviso de éxito (`role="status"`)                  | —                     | «Artista registrado.» (al llegar desde el alta) · «Cambios guardados.» (tras un `PUT`) |

- El formulario es un único componente, `ArtistForm`, que usan las dos páginas. Lleva `noValidate`: la validación del navegador no interviene y los mensajes son siempre los de §3.3.
- No se muestran `id`, `status` ni fechas.

### 3.3 Validación en el cliente (Zod)

Solo adelanta lo obvio. El servidor es la fuente de verdad (backend §3.3) y lo que el cliente no valida lo devuelve el 422.

| Campo   | Regla en el cliente                     | Mensaje                         |
| ------- | --------------------------------------- | ------------------------------- |
| `name`  | Obligatorio (vacío tras recortar = falta) | «El nombre es obligatorio.»     |
| `email` | Obligatorio (vacío tras recortar = falta) | «El email es obligatorio.»      |
| `email` | Formato de email                        | «Ingresa un email válido.»      |

- **No** se valida el máximo de 255 ni la unicidad: el valor vive en el backend y duplicarlo es el drift que prohíbe la metodología §0 (decisión del 2026-10-06).
- Si hay errores de cliente, **no se envía ninguna petición**.
- Un campo con error lleva `aria-invalid="true"` y su mensaje visible debajo.
- El email se envía tal como lo escribió el usuario (recortado). La conversión a minúsculas es del backend (§3.3 de la contraparte).

### 3.4 Datos (TanStack Query + `api`)

- Todas las llamadas usan `api` de `src/lib/api.ts`. El cuerpo enviado es exactamente `{ name, email }` en `POST` y en `PUT` (semántica PUT: representación editable completa, backend §3.1).
- Tipo `Artist` con la forma de `ArtistResource` (backend §3.5). La envoltura `data` se quita en la función de consulta o de mutación.
- **Precarga:** `useQuery` con clave `['artists', id]`. El formulario no se pinta hasta tener los datos; mientras tanto se muestra «Cargando…».
- **Alta:** `useMutation`. Con el 201, se guarda la respuesta en la caché `['artists', id]` y se navega a `/artistas/{id}/editar` con el estado de navegación que dispara el aviso «Artista registrado.».
- **Edición:** `useMutation`. Con el 200, se actualiza la caché `['artists', id]` y el formulario pasa a mostrar los valores **devueltos por el servidor** (p. ej., el email ya en minúsculas).
- **Envío en curso:** el botón queda deshabilitado; un segundo clic no genera otra petición.

### 3.5 Errores (por `code`, D3.1)

| Situación                                               | Qué se muestra                                                                                   |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 422 `VALIDATION_ERROR` con `errors.name` / `errors.email` | El **primer mensaje** de cada campo, tal como llega, en ese campo (`setError`). Se conservan los valores escritos. |
| 422 `VALIDATION_ERROR` sin `errors` o solo con otros campos | Aviso general (`role="alert"`): «Revisa los datos del formulario.»                              |
| Precarga con 404 `RESOURCE_NOT_FOUND`                   | Encabezado «Artista no encontrado» y **sin formulario**.                                        |
| Precarga con cualquier otro error                       | «No se pudo cargar el artista.» y sin formulario.                                               |
| Envío con cualquier otro error (500, red, 404 en `PUT`) | Aviso general (`role="alert"`): «No se pudo guardar el artista. Inténtalo de nuevo.» Se conservan los valores. |
| 401 / 403                                               | Nada propio: los resuelve el interceptor de HU-04.                                              |

- Ninguna rama mira `message`, `title` ni `detail`; solo `code`, el estado de la respuesta y las **claves** de `errors`.
- Los textos de `errors.<campo>` llegan en español desde la API ([`../backend/HU-05.md`](../backend/HU-05.md) §3.8). El frontend no los traduce ni los reescribe.

## 5. Notas de implementación (para el humano)

- **Reutilizar:** `api` y `ApiErrorBody` (`src/lib/api.ts`), `RequireAuth`/`RequireRole`, `Button` (`components/ui/button.tsx`). El patrón de `useQuery` de `routes/Me.tsx`.
- **Faltan componentes de shadcn:** `npx shadcn add input label` (estilo `base-nova`, ver `components.json`). Es código de aplicación: lo ejecutas tú.
- **Orden sugerido de Green:** rutas en `App.tsx` (#12) → `ArtistForm` con Zod (#2, #3) → `ArtistCreatePage` (#1, #6) → errores del alta (#4, #5, #7) → `ArtistEditPage` (#8–#11).
- **Formulario:** `useForm` con `zodResolver`. En la edición, los valores iniciales llegan con la consulta: usa la opción `values` de React Hook Form o un `reset` cuando llegan los datos, para que #8 y #9 vean los valores del servidor.
- **422 → campos:** recorre `error.response.data.errors` y llama a `setError(campo, { message: mensajes[0] })` solo para `name` y `email`. Si no queda ninguno, aviso general (#5). Distingue el 422 por `code === 'VALIDATION_ERROR'`, no por el texto.
- **Navegación tras el alta:** `` navigate(`/artistas/${id}/editar`, { state: … }) ``. La página de edición lee ese estado para el aviso.
- **Doble envío:** basta con deshabilitar el botón con `isSubmitting` del formulario o con `isPending` de la mutación, siempre que el `onSubmit` espere a la mutación (`mutateAsync`).
- **Trampa:** sin `noValidate`, un `input type="email"` puede bloquear el envío con la validación nativa del navegador y #2 vería un mensaje distinto.
- `graphify` no está instalado en esta máquina; los símbolos reutilizados se localizaron con búsqueda dirigida.
