Los criterios de aceptación viven en Jira. El contrato de `analysis` y `technical_check` vive en la spec backend (§3.2 y §3.4) y aquí solo se referencia. Esta spec define:

- cómo se calcula el análisis en el navegador sin frenar la interfaz ni la subida;
- qué se envía en la confirmación, y el reintento ante un 422;
- cómo se pinta el chequeo que devuelve el backend;
- la prueba de precisión contra `ffmpeg`.

## 1. Alcance en esta capa

**Dentro:**

- **Cálculo en un Web Worker** (D7.9) del volumen integrado (BS.1770-4), el pico real, la saturación, los silencios y las series por segundo de volumen y de las tres bandas. El WAV se lee por partes (`File.slice`). El MP3 lo decodifica el navegador (§3.3).
- **En paralelo con la subida:** el análisis arranca a la vez que la firma. Si no ha terminado cuando S3 responde, la confirmación espera como mucho un margen fijo; pasado ese margen, se confirma sin análisis (§3.5).
- **Topes:** más de 20 min, MP3 de más de 10 min, formato de WAV no soportado o un fallo del análisis → la versión se sube «sin análisis». El formulario lo avisa (marco 14b).
- **Confirmación** con `analysis`. Ante un 422 con claves `analysis…`, se reintenta una sola vez sin él (backend §3.2).
- **Chequeo en el reproductor** (marcos 11-13 y 15): una sección «Chequeo técnico» con insignia y cuatro tarjetas.
- **Insignia en cada tarjeta del historial** (marco 5): «N advertencias», «Chequeo sin advertencias» o «Sin análisis».
- **Precisión:** una prueba automatizada contra `ffmpeg -af ebur128=peak=true` con archivos de referencia (§3.4).

**Fuera / diferido (con motivo):**

- **Series en pantalla** (gráficas de volumen y bandas) → `TS-93` (A/B). Aquí solo se calculan y se envían; el backend no las devuelve (backend §1).
- **Volver a analizar** una versión ya verificada o antigua → no. La confirmación es idempotente (backend §3.3), y las versiones anteriores a `TS-91` quedan «sin análisis» (D7.9).
- **Descargar el resumen como artista** (D7.9) → HU-21 parte B. El artista ve lo mismo que el productor en el historial cuando tenga acceso; esta spec no añade nada para él.
- **Reglas del chequeo:** no se duplican. `ok`, `warning` y `not_applicable` llegan del backend (D7.10). La única regla que repite el cliente es qué silencios se listan (§3.7, decisión pendiente n.º 4).
- **Estilo final** de las tarjetas del historial y del reproductor → `TS-73`/`TS-74`. Aquí, la estructura y los estados de los marcos con las clases de Tailwind que ya usa la app.
- **Librerías de audio:** no. La Web Audio API y unas cien líneas de DSP bastan (D7.9, `frontend/CLAUDE.md`).

## 3. Contrato técnico

### 3.1 Dónde vive

### 3.2 Tipos (`versionSchema.ts`)

```ts
export const MAX_ANALYSIS_MS = 1_200_000      // 20 min = 1200 tramos (backend §3.2)
export const MAX_MP3_ANALYSIS_MS = 600_000    // 10 min: memoria del MP3 decodificado (§3.3)
export const ANALYSIS_GRACE_MS = 15_000       // espera máxima tras S3 (§3.5)

export type CheckState = 'ok' | 'warning' | 'not_applicable'

export interface Silence { start_ms: number; end_ms: number }

/** Lo que devuelve el backend: sin `series` (backend §3.4). */
export interface VersionAnalysis {
  schema_version: 1
  integrated_lufs: number | null
  true_peak_dbtp: number | null
  clipped_samples: number
  clip_events: number
  silences: Silence[]
}

/** Lo que se envía al confirmar (backend §3.2). */
export interface AnalysisPayload extends VersionAnalysis {
  series: Record<'loudness' | 'low' | 'mid' | 'high', (number | null)[]>
}

export interface TechnicalCheckResult {
  checks: Record<'integrated_lufs' | 'true_peak' | 'clipping' | 'silence', CheckState>
  thresholds: {
    integrated_lufs_target: number
    integrated_lufs_tolerance: number
    true_peak_max_dbtp: number
    clip_events_min: number
    silence_min_ms: number
  }
}

// Version suma, al final:
//   analysis: VersionAnalysis | null
//   technical_check: TechnicalCheckResult | null

export type NoAnalysisReason = 'duracion' | 'mp3' | 'formato' | 'error'
export type AnalysisOutcome =
  | { analysis: AnalysisPayload }
  | { analysis: null; reason: NoAnalysisReason }
```

`MAX_ANALYSIS_MS` es la frontera del backend en milisegundos. Se repite aquí porque el backend no la expone. Un test (§4.3 #13) fija que 1.200.000 ms aún se analiza y que 1.200.001 ms ya no.

### 3.3 Lectura del audio

**WAV (`readWav`, dentro del Worker):**

- **Cabecera:** se leen los primeros 64 KB con `File.slice` y se recorren los chunks RIFF hasta `fmt ` y `data`:
  - se saltan los desconocidos (`LIST`, `bext`, `JUNK`…);
  - un chunk de tamaño impar lleva un byte de relleno.
  - Si `data` está más allá de los 64 KB, se lee la cabecera de cada chunk con otro `slice`.
- **Formatos soportados:**
  - PCM entero (`format 1`, o `0xFFFE` *extensible* con subformato PCM) de 16, 24 o 32 bits;
  - flotante IEEE (`format 3`, o extensible con subformato float) de 32 bits.
  - Entre 1 y 2 canales.
  - Cualquier frecuencia de muestreo entre 8 y 192 kHz.
  - Todo lo demás (8 bits, ADPCM, más de 2 canales, cabecera rota) → `reason: 'formato'`.
- **Normalización:** las muestras se pasan a `Float32Array` por canal, en [−1, 1). Los enteros se dividen por 2^(bits−1).
- **Lectura por partes:** bloques de 4 MiB alineados a `blockAlign`. Cada bloque se mide y se descarta, así que la memoria no crece con el archivo. El progreso es `bytes leídos / tamaño de data`.

**MP3 (`startAnalysis`, en el hilo principal):**

- `decodeAudioData` no existe en un Worker. Se decodifica con `new OfflineAudioContext(1, 1, 48000).decodeAudioData(await file.arrayBuffer())`; el navegador decodifica fuera del hilo principal y remuestrea a 48 kHz.
- Los canales (`getChannelData`, copiados) se envían al Worker como `Transferable`, y el Worker los mide en bloques de 1 s.
- **Tope de 10 min:** un MP3 estéreo de 10 min decodificado ocupa unos 230 MB en `float32`. A partir de ahí el riesgo de quedarse sin memoria en un portátil modesto deja de ser aceptable (decisión pendiente n.º 2).

**Topes, en este orden y antes de leer nada:**

| Condición | Resultado |
| --- | --- |
| `durationMs > MAX_ANALYSIS_MS` | `{ analysis: null, reason: 'duracion' }`, sin crear el Worker. |
| MP3 con `durationMs > MAX_MP3_ANALYSIS_MS` | `{ analysis: null, reason: 'mp3' }`, sin decodificar. |
| Formato de WAV no soportado | `{ analysis: null, reason: 'formato' }` |
| Error del Worker, del decodificador o una excepción | `{ analysis: null, reason: 'error' }` |

`result` **nunca rechaza**: todo fallo acaba en `analysis: null` (D7.9: el análisis nunca bloquea). `cancel()` termina el Worker y resuelve `result` con `reason: 'error'`.

### 3.4 Medición (`createMeter`)

`createMeter(sampleRate, channels)` devuelve `{ push(channels: Float32Array[]): void; finish(durationMs: number): AnalysisPayload }`. Todo se calcula en una pasada y con memoria acotada: se guardan solo las energías por bloque de 100 ms, del orden de 12.000 números para 20 min.

**Volumen integrado** (ITU-R BS.1770-4, igual que `ffmpeg ebur128`):

1. **Ponderación K:** dos biquads por canal, calculados para cualquier `sampleRate` con la transformación bilineal de libebur128:
   - *shelf*: f0 = 1681,974450955533 Hz, G = 3,999843853973347 dB, Q = 0,7071752369554196;
   - *high-pass*: f0 = 38,13547087602444 Hz, Q = 0,5003270373238773.
2. **Bloques:** de 400 ms con solape del 75 %, armados desde subbloques de 100 ms.
3. **Energía por bloque:** z = Σ_canal (media de x²), con peso 1,0 para L y R. Un WAV mono es un solo canal con peso 1,0, sin *dual mono*, como el valor por defecto de `ffmpeg`.
4. **Volumen de un bloque:** L = −0,691 + 10·log10(z).
5. **Compuertas:** primero la absoluta (−70 LUFS) y luego la relativa (−10 LU sobre la media de los bloques que pasan la absoluta).
6. **Resultado:**
   - `integrated_lufs` = −0,691 + 10·log10(media de z de los bloques que pasan las dos compuertas);
   - si ningún bloque pasa la absoluta, `null`.

**Pico real:**

- Sobremuestreo con el FIR polifásico de 48 coeficientes del anexo 2 de BS.1770-4 (4 fases de 12):
  - 4× si `sampleRate ≤ 48 kHz`;
  - 2× (fases 0 y 2) si `≤ 96 kHz`;
  - 1× por encima.
- `true_peak_dbtp` = 20·log10(máximo |y| entre canales y fases). Si el máximo es 0 (silencio digital), `null`.
- `ffmpeg` sobremuestrea a 192 kHz con otro filtro, de ahí la tolerancia de ±0,5 dB (D7.9).

**Saturación** (D7.10):

- Una muestra está saturada si |x| ≥ 1,0 tras normalizar. En enteros, eso es el valor mínimo; el máximo positivo, 32767/32768, se cuenta aparte con `x ≥ (2^(bits−1) − 1) / 2^(bits−1)`. En flotante, |x| ≥ 1,0.
- `clipped_samples` es el total de muestras saturadas, contando cada canal por separado.
- `clip_events` es el número de rachas de 3 o más muestras saturadas seguidas **en el mismo canal**, también entre dos bloques de lectura. Por construcción, `clip_events × 3 ≤ clipped_samples` (backend §3.2).

**Silencios:**

- **Ventanas:** de 100 ms. Una ventana es silencio si su **pico de muestra** (el máximo |x| entre canales) es menor que 10^(−60/20), es decir, −60 dBFS. Se usa el pico y no el RMS para no marcar como silencio las colas de reverberación (decisión pendiente n.º 3).
- **Tramos:** cada racha de ventanas silenciosas da un tramo con `start_ms = round(primer frame / sampleRate × 1000)` y `end_ms = min(round(frame final / sampleRate × 1000), durationMs)`.
- **Filtro:** se conservan los tramos de 1000 ms o más **tras** el recorte (backend §3.2), incluidos los del inicio y el final.
- **Orden:** como dos tramos los separa al menos una ventana con sonido, cada `start_ms` es mayor que el `end_ms` anterior.

**Series** (una entrada por segundo; longitud **exactamente** `ceil(durationMs / 1000)`):

- `durationMs` es el que se envía en la confirmación, el de `readDurationMs`. Si las muestras dan un segundo más, se recorta; si dan uno menos, se rellena con `null`. El último segundo puede ser parcial.
- `loudness[i]` = −0,691 + 10·log10(Σ_canal media de x² ponderada K) en el segundo i, sin compuertas.
- `low`, `mid` y `high`:
  - 10·log10(media entre canales de la media de x²) de la señal filtrada, sin ponderar;
  - filtros Butterworth de 2.º orden (RBJ, Q = 0,7071): `low` = paso bajo a 250 Hz; `mid` = paso alto a 250 Hz más paso bajo a 4 kHz; `high` = paso alto a 4 kHz.
- Un valor menor de −120, o con energía 0, es `null`. Ninguno puede pasar de +20 dB con muestras en [−1, 1], pero se recorta a 20 por contrato.

**Redondeo:** todos los valores en dB se redondean a 1 decimal (`Math.round(x * 10) / 10`, y −0 pasa a 0). Los conteos son enteros. `schema_version: 1`.

### 3.5 Subida (`VersionUpload`, cambia HU-14 §3.4)

El orden de `mutationFn` pasa a ser:

1. **Lanzar el análisis:** `const job = startAnalysis(file, contentType, durationMs, setAnalysisProgress)`. Sin `await`: corre en paralelo.
2. **Firmar y subir a S3**, como hoy. Si falla, `job.cancel()` y se lanza el error como hoy.
3. **Esperar el análisis:** `await` de `job.result`, con un tope de `ANALYSIS_GRACE_MS` desde que S3 responde. Pasado el tope, `job.cancel()` y se sigue sin análisis. Mientras espera, la fase es `'analizando'`.
4. **Confirmar:** `phase = 'verificando'` y `confirmVersion(id, etag, durationMs, analysis ?? undefined)`.
5. **Reintento único:** si el paso 4 da 422 `VALIDATION_ERROR` y alguna clave de `errors` es `analysis` o empieza por `analysis.`, se confirma otra vez **sin** `analysis`. El resultado de ese segundo intento se trata como hoy: éxito o `VerifyError`.

El análisis nunca bloquea ni retrasa la subida (AC): la firma y el POST a S3 no esperan por él. Solo la confirmación espera, y como mucho 15 s (decisión pendiente n.º 1). Al desmontar el formulario, `job.cancel()`.

**Textos (marcos 14 y 14b), todos con `role="status"` salvo las barras:**

| Momento | Qué se ve |
| --- | --- |
| Subiendo y analizando | `<progress aria-label="Progreso de la subida">` + «Subiendo… {n} %» (sin cambios) y debajo `<progress aria-label="Progreso del análisis">` + «Analizando el audio… {n} %». |
| S3 terminó y el análisis no | Solo la barra del análisis, con «Terminando el análisis… {n} %». |
| `reason: 'duracion'` | «Esta versión se subirá sin análisis técnico: dura más de 20 minutos.» |
| `reason: 'mp3'` | «Esta versión se subirá sin análisis técnico: es un MP3 de más de 10 minutos.» |
| `reason: 'formato'` | «Esta versión se subirá sin análisis técnico: el formato del WAV no se puede analizar.» |
| `reason: 'error'` o tope de espera | «No se pudo analizar el audio; la versión se subirá sin análisis técnico.» |

El aviso de `duracion` y `mp3` aparece en cuanto se conoce, antes de firmar, porque `startAnalysis` lo resuelve sin crear el Worker. El de `formato` y `error`, cuando ocurre. Tras el éxito queda «Versión v{n} verificada.» y el aviso se limpia, como el resto del formulario.

### 3.6 `confirmVersion` (`versionApi.ts`)

```ts
confirmVersion(versionId: string, etag: string, durationMs: number, analysis?: AnalysisPayload)
```

Envía `analysis` solo si está definido: sin análisis, la clave **no aparece** (ni siquiera como `null`). Así el cuerpo de HU-14 sigue idéntico y sus tests no cambian. Los números van como números JSON (backend §3.2, «números estrictos»).

### 3.7 El chequeo en pantalla

**Dónde se ve:**

- En cada `<li>` del historial (`VersionHistory`), tras la fecha, va la insignia `TechnicalCheckBadge` (marco 5, slot «Meta»).
- En el reproductor (`VersionPlayer`), bajo el `<audio>` y antes de la barra de comentarios, va la sección `TechnicalCheck` de la versión seleccionada (marcos 11-13). Es una `<section aria-labelledby>` con un `<h3>` «Chequeo técnico».

**Insignia** (cuenta los `warning` de `technical_check.checks`):

| Caso | Texto | Ícono |
| --- | --- | --- |
| `technical_check === null` | «Sin análisis» | `CircleMinus`, tono apagado |
| 0 `warning` | «Chequeo sin advertencias» | `Check`, verde |
| 1 | «1 advertencia» | `TriangleAlert`, ámbar |
| n > 1 | «{n} advertencias» | `TriangleAlert`, ámbar |

**Sección sin análisis** (marco 13): el encabezado con la insignia «Sin análisis» y el párrafo «Esta versión no tiene análisis técnico: se subió antes de esta función, dura más de 20 minutos o el análisis no terminó. Se puede escuchar igual.» Sin tarjetas.

**Tarjetas** (con análisis):

- **Estructura:** una lista (`<ul>`) de cuatro `<li>`, cada uno con etiqueta, valor y referencia. La rejilla es `grid-cols-2` en móvil y `md:grid-cols-4` en escritorio (marcos 11 y 15).
- **Estado:** cada tarjeta lleva un texto solo para lectores de pantalla (`sr-only`) que lo nombra: «Correcto», «Advertencia» o «No se revisa». El ícono es `aria-hidden`.
- **Borde:** las de `warning` llevan el borde ámbar.

| Tarjeta | Estado de | Valor | Referencia |
| --- | --- | --- | --- |
| Volumen integrado | `checks.integrated_lufs` | `formatDb(integrated_lufs)` + « LUFS»; «—» si es `null` | `ok`/`warning`: «Referencia: {formatDb(target)} ± {formatNumber(tolerance)} LUFS». `not_applicable` con valor: «Solo se revisa en el master». `null`: «Sin señal medible». |
| Pico real | `checks.true_peak` | `formatDb(true_peak_dbtp)` + « dBTP»; «—» si es `null` | `ok`/`warning`: «Referencia: ≤ {formatDb(max)} dBTP». `not_applicable`: igual que el volumen. |
| Saturación | `checks.clipping` | «Ninguna», «1 evento» o «{n} eventos» (`clip_events`) | «Referencia: ninguno» si `clip_events_min` es 1; si no, «Referencia: menos de {min} eventos». |
| Silencios | `checks.silence` | «Ninguno», «1 tramo» o «{n} tramos» (los listados abajo) | Con tramos: «{formatTimestamp(start)} – {formatTimestamp(end)}», separados por « · », y luego « · tramos de {min/1000} s o más». Sin tramos: «Tramos de {min/1000} s o más». |

- **Formato de números:** `formatDb(x)` usa `Intl.NumberFormat('es', { minimumFractionDigits: 1, maximumFractionDigits: 1, signDisplay: 'exceptZero' })` y cambia `-` por `−` (U+2212, como en los marcos). Da «−13,4», «+0,4» y «0,0». `formatNumber` es igual pero sin signo.
- **Silencios listados:** los de `analysis.silences` con `start_ms > 0`, `end_ms < duration_ms` y `end_ms − start_ms ≥ thresholds.silence_min_ms`. Es la regla del backend (§3.4). El estado y la insignia vienen siempre de `checks.silence`, así que si las dos copias divergen solo cambia la lista, nunca la advertencia (decisión pendiente n.º 4).
- **Texto de `not_applicable`:** cambia el del marco 12, «No se revisa en mezclas», porque `not_applicable` también cubre voz, instrumentos, arreglo, otro y sin categoría.
- **Nota al pie:** «Advierte, no bloquea: el productor decide. Volumen y pico se juzgan solo en versiones «Master»; saturación y silencios, en todas.»

### 3.8 Accesibilidad (RNF-07)

- Las dos barras de progreso tienen nombre accesible propio, y los avisos van con `role="status"`.
- El estado de cada tarjeta se anuncia con texto, no solo con color e ícono.
- La insignia es texto plano, así que la lee el lector de pantalla dentro del `<li>` de la versión.
- El contraste del ámbar sobre el fondo es el de los marcos, y se revisa en `TS-74`.

### 4.1 Medición — `audioAnalysis.test.ts` (señales sintéticas generadas en el test)

1. **Volumen de referencia:** un seno de 1 kHz a −23 dBFS en estéreo, a 48 kHz y durante 10 s, da `integrated_lufs` −23,0 ± 0,1 (EBU Tech 3341, caso 1).
2. **Silencio digital:** 5 s de ceros dan `integrated_lufs: null`, `true_peak_dbtp: null` y `clipped_samples: 0`. Las cuatro series dan solo `null` y los silencios son `[{ start_ms: 0, end_ms: 5000 }]`.
3. **Pico real:** un seno a fs/4 con fase de 45° y amplitud 1,0 tiene un pico de muestra de −3,0 dBFS y un pico real de 0,0 ± 0,5 dBTP.
4. **Saturación:** rachas de 2, 3 y 5 muestras a fondo de escala en el canal L, y una de 3 que cruza dos `push` en el canal R, dan `clipped_samples: 13` y `clip_events: 3`. En PCM de 16 bits, tanto −32768 como 32767 cuentan.
5. **Silencios:** con el patrón tono, 1,5 s de silencio, tono, 0,8 s de silencio y tono, solo se detecta el tramo de 1,5 s, con sus bordes a ±100 ms. Un silencio que llega al final recorta su `end_ms` a `durationMs`, y si tras el recorte dura menos de 1000 ms, desaparece.
6. **Longitud de las series:** con `durationMs` de 4001 se generan 5 valores, aunque las muestras den 4 s exactos (el último es `null`). Con 3999 ms y 4 s de muestras, se generan 4.
7. **Bandas:** un tono de 100 Hz da `low` al menos 20 dB por encima de `mid` y `high`. Uno de 1 kHz da `mid` dominante y uno de 8 kHz, `high` dominante.
8. **Lectura WAV:**
   - lee bien 16, 24 y 32 bits enteros, 32 flotante y *extensible*;
   - salta `LIST` y el byte de relleno de un chunk impar;
   - lee la cabecera de `data` más allá de los primeros 64 KB.
   - 8 bits, 3 canales, ADPCM y un archivo sin `fmt ` dan `reason: 'formato'`.
9. **Forma del contrato:**
   - las claves son exactamente las de backend §3.2, con `schema_version: 1`;
   - los dB tienen como mucho 1 decimal y no hay −0;
   - todos los valores son `number` o `null`, nunca cadenas;
   - se cumple `clip_events × 3 ≤ clipped_samples`;
   - los silencios están ordenados y no se tocan.

## 5. Notas de implementación para el equipo

- **Orden sugerido:** `audioAnalysis.ts` (#1-#10) → `startAnalysis.ts` y el worker (#11-#15) → `VersionUpload` (#16-#21) → `TechnicalCheck` y su integración (#22-#28).
- **Los coeficientes de BS.1770** (la ponderación K y los 48 del FIR del anexo 2) van como constantes con comentario de procedencia. Son datos de la norma, no lógica.
- **El progreso** del Worker se envía como mucho 10 veces por segundo, porque más mensajes saturan el hilo principal sin aportar nada. `setAnalysisProgress` redondea a entero.
- **`Transferable`:** el `File` se envía al Worker por copia estructurada, que no duplica los bytes. Los `Float32Array` del MP3, con `postMessage(msg, [buf.buffer])`.
- **Vite** empaqueta el worker solo con `new URL(..., import.meta.url)`. En Vitest (jsdom) no hay `Worker`, así que los tests de §4.3 lo sustituyen y los de §4.4 sustituyen el módulo entero.
- **Datos de prueba del backend:** `datosDeAnalisis` (`backend/tests/Pest.php`) es la referencia de forma. Conviene que el doble del frontend (`src/test/analisis.ts`) use los mismos números (−9,8, 0,4, 12 y 2, y el silencio 61000-64500), para que un vistazo a los dos lados coincida.
- **`ffmpeg`** (con `libmp3lame`) solo hace falta para dos cosas: regenerar las referencias (`scripts/ebur128-fixtures.sh`, que reescribe `references.json`) y generar el juego de demo (`scripts/audio-demo.sh`). Ninguno corre en CI. En local hay `ffmpeg n9.1`. Los dos scripts y la línea de `.gitignore` se escriben en `.06`, con los tests.
