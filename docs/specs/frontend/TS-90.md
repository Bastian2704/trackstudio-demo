## 1. Alcance en esta capa

**Dentro:**

- `VersionUpload`: grupo de radios «¿Qué cambió?» con las 6 categorías y el texto del motivo, obligatorios u opcionales según la canción ya tenga una versión verificada (§3.2). Errores en su campo (§3.5).
- `VersionHistory`: la categoría junto al título de la versión (§3.6). El texto ya se muestra hoy (`description`).
- `versionSchema.ts`: tipo `ChangeCategory`, la lista con sus textos y `change_category` en `Version`.
- `versionApi.ts`: `createVersion` acepta `change_category` en `extras`.

**Fuera / diferido (con motivo):**

- Editar el motivo → el AC lo prohíbe (backend §1).
- Fidelidad visual del resto del formulario y de la tarjeta del historial (marco 4: número grande, formato, tarjeta con borde) → `TS-73`. Aquí solo se construyen lo nuevo (chips y etiqueta de categoría) con el estilo del marco, y el resto se queda como está.
- El motivo en la comparación A/B → `TS-93` (S6).
- El artista no sube versiones; ve la categoría en el historial que ya lee (HU-21), sin cambios de rol.

## 3. Contrato técnico

### 3.1 Tipos y API

```ts
// versionSchema.ts
export const CHANGE_CATEGORIES = [
  { value: 'voz', label: 'Voz' },
  { value: 'instrumentos', label: 'Instrumentos' },
  { value: 'mezcla', label: 'Mezcla' },
  { value: 'master', label: 'Master' },
  { value: 'arreglo', label: 'Arreglo' },
  { value: 'otro', label: 'Otro' },
] as const
export type ChangeCategory = (typeof CHANGE_CATEGORIES)[number]['value']
// Version gana: change_category: ChangeCategory | null
```

`createVersion(..., extras: { label?; description?; change_category? })`. La lista es la única copia en el cliente; el orden es el del marco.

### 3.2 ¿Obligatorio u opcional?

`VersionUpload` lee la **misma consulta que la página 1 del historial**: `useQuery({ queryKey: ['versions', 'list', songId, 1], queryFn: () => fetchVersions(songId, 1) })`. Con `VersionHistory` en la misma página, React Query la comparte y no hay una segunda petición.

| Estado de la consulta | Modo |
| --- | --- |
| `meta.total > 0` | **Obligatorio** (marco 1) |
| `meta.total === 0` | **Opcional** (marco 2) |
| Cargando o con error | **Opcional**. El servidor decide: si la canción sí tenía una verificada, su 422 pinta los errores (§3.5). |

Tras una subida verificada ya se invalida `['versions', 'list', songId]` (HU-14), así que el formulario pasa solo a modo obligatorio después de la primera versión.

### 3.3 Textos

| Elemento | Modo obligatorio | Modo opcional |
| --- | --- | --- |
| Leyenda del grupo | «¿Qué cambió?» + `*` visual | «Categoría (opcional)» |
| Ayuda bajo la leyenda | — | «La primera versión no necesita motivo. Si eliges una categoría, describe el cambio.» |
| Etiqueta del texto | «¿Qué cambió y por qué?» + `*` visual | «Descripción (opcional)» |
| Contador | `{n} / 1000`, con `n = description.length` | igual |
| Quitar la categoría | — | botón «Quitar categoría», visible solo con una categoría elegida (marco 2b) |
| Etiqueta del texto con categoría elegida | — | «¿Qué cambió y por qué?» + `*` y `aria-required`, porque el texto pasa a ser obligatorio (§3.4.3); al quitar la categoría vuelve a «Descripción (opcional)» |

- El `*` va en un `<span aria-hidden="true">`; lo obligatorio se anuncia con `aria-required="true"` en el grupo y en el texto.
- El contador usa `length` (UTF-16), igual que el `maxLength={1000}` que ya tiene el campo: el cliente nunca deja pasar más de lo que acepta el backend (`max:1000` en puntos de código, que siempre son ≤ unidades UTF-16).

### 3.4 Envío

En `submit`, **antes** de validar el archivo (es instantáneo y no toca la red):

1. Modo obligatorio y falta la categoría → error de campo «Elige qué cambió en esta versión.».
2. Modo obligatorio y el texto (tras `trim`) está vacío → error de campo «Explica qué cambió y por qué.».
3. Modo opcional, con categoría y sin texto → error de campo «Explica qué cambió y por qué.».
4. Si hay algún error, no se firma. Los dos errores se muestran juntos (decisión del backend §7.2).

Los mensajes son los del backend (§3.3 de su spec), para que el usuario vea lo mismo venga de donde venga. El cuerpo de la firma incluye `change_category` solo si hay una elegida, como ya se hace con `label` y `description`. Tras una subida verificada se vacía también la categoría.

### 3.5 Errores (D3.1)

- 422 `VALIDATION_ERROR` con `errors.change_category` o `errors.description` → el mensaje del servidor bajo **su** campo, no en el `ErrorAlert` general. Se decide por `code` y por la clave de `errors`, nunca por el estado HTTP (trampa de v44).
- El resto de errores sigue igual (alerta general de HU-13/HU-14).
- Al cambiar la categoría o el texto se borra el error de ese campo.

### 3.6 Historial

En cada versión con `change_category`, una etiqueta con el texto de `CHANGE_CATEGORIES` junto al título (componente «Etiqueta de categoría»: fondo `primary` claro al 12 %, texto `#cabeff`, 11 px semibold). Sin categoría, la versión se ve como hoy. El texto del motivo ya sale (`description`).

### 3.7 Accesibilidad (RNF-07)

- Grupo: `<fieldset>` con `<legend>`, `role="radiogroup"` implícito de los radios nativos; flechas para moverse, como cualquier grupo de radios.
- Cada chip es un `<label>` con su `<input type="radio" name="change_category">` visualmente oculto (`sr-only`) y foco visible en el chip (`has-[:focus-visible]:ring`).
- Errores: `aria-invalid="true"` y `aria-describedby` hacia el mensaje, en el grupo y en el texto.

## 4. Criterios de aceptación de esta capa → tests (Vitest)

`VersionUpload.test.tsx`, describe nuevo «motivo (TS-90)», y `VersionHistory.test.tsx`. **Enmienda:** `renderSubida` y los simuladores de los tests de HU-13/HU-14 responden también al `GET …/versions` (con `total: 0` por defecto, que deja el formulario como hoy).
