## 3. Contrato técnico

### 3.1 `Auth0Provider` (`src/main.tsx`)

| Prop | Valor | Por qué |
| --- | --- | --- |
| `domain`, `clientId` | `VITE_AUTH0_DOMAIN`, `VITE_AUTH0_CLIENT_ID` | Tenant y app SPA de `ts-03.10`. |
| `authorizationParams.audience` | `VITE_AUTH0_AUDIENCE` | **Sin audience, Auth0 emite un token opaco** que el guard del backend rechaza con 401. Es el mismo valor que `AUTH0_AUDIENCE` del backend. |
| `authorizationParams.redirect_uri` | `window.location.origin` | Vuelve a la raíz; `Home` redirige a `/me` si hay sesión. |
| `useRefreshTokens` | `true` | D5.1: con el token en memoria, recargar la página pierde el caché; la sesión sigue gracias al refresh token con rotación. |
| `cacheLocation` | `"memory"` | D5.1. Ya es el valor por defecto del SDK, pero se declara explícito para que el review lo vea. Su efecto lo prueba `HU-04.md` test 4. |

Variables de entorno: `.env.example` del frontend (sin valores reales, regla §0.5). `VITE_AUTH0_ROLE_CLAIM` también vive ahí, pero la consume HU-04.

### 3.2 Login, logout y ruta privada

- **Login:** `LoginButton` llama a `loginWithRedirect()` sin argumentos (Universal Login de Auth0).
- **Logout:** `LogoutButton` llama a `logout({ logoutParams: { returnTo: window.location.origin } })`. Cierra la sesión **en Auth0**, no solo la local; si no, el siguiente login entraría sin pedir credenciales. `returnTo` debe estar entre los *Logout URLs* de la app SPA.
- **`RequireAuth`:** envuelve las rutas privadas con `withAuthenticationRequired`. Sin sesión no renderiza el contenido y manda a login.

### 3.3 Interceptor de request (`src/lib/api.ts`)

- `attachAuthInterceptor(getAccessToken)` registra un interceptor en la instancia `api`, que es la única que habla con el backend (`baseURL = VITE_API_BASE_URL`).
- **El token se pide en cada request**, no al registrar el interceptor. `getAccessTokenSilently` devuelve el token en caché o lo renueva; si se guardara una sola vez, la app mandaría un token vencido al cabo de su `exp`.
- **Si no hay token, la petición no sale.** Si `getAccessToken` rechaza (sesión caducada, `login_required`), la promesa del interceptor rechaza y axios no envía nada. Nunca se manda una petición sin `Authorization`, ni con `Bearer undefined`, para "ver qué pasa".
- `App.tsx` registra el interceptor en un `useEffect` y lo retira (`eject`) al desmontar, para no acumular interceptores duplicados con `StrictMode`.

### 3.4 Página de humo `/me` — corrige un drift

Contrato de la contraparte (backend §3.4), que **manda**:

```json
{ "data": { "sub": "auth0|…", "role": "productor" } }
```

`role` es `"productor"`, `"artista"` o `null`.

**Drift actual (`src/routes/Me.tsx:7-12`):** la página tipa la respuesta como `{ id, email, name, role }`. El backend no devuelve `id`, `email` ni `name`: no vienen en el access token (backend §3.4, corrección del 2026-09-17). Nombre y correo, si se quieren mostrar, salen de `useAuth0().user` (ID token), no de `/me`. Además, el mensaje de error de la línea 41 ("el backend aún no expone este endpoint") ya es falso.

**Corrección (humano, reabre `ts-03.07`):**

- El tipo pasa a `{ sub: string; role: 'productor' | 'artista' | null }`.
- La página muestra `sub` y `role` de la respuesta.
- El mensaje de error muestra el `code` de D3.1 sin afirmar nada sobre el backend.

## 4. Criterios de aceptación de esta capa → tests (Vitest + RTL)

Los tests conviven con el código, como `src/lib/utils.test.ts`. El SDK de Auth0 se mockea (`vi.mock('@auth0/auth0-react')`): aquí se prueba nuestro uso del SDK, no Auth0. La frontera real es `ts-03.09`.

| # | Test (archivo::caso) | Qué afirma | Cómo se prueba que FALLA (C3) |
| --- | --- | --- | --- |
| 1 | `components/LoginButton.test.tsx::al pulsar llama a loginWithRedirect` | Un clic en el botón llama una vez a `loginWithRedirect`. | Quitar el `onClick` o cambiarlo por un no-op → rojo. |
| 2 | `components/LogoutButton.test.tsx::cierra sesión en Auth0 y vuelve al origen` | Un clic llama a `logout` con `logoutParams.returnTo === window.location.origin`. | Llamar a `logout()` sin `returnTo`, o con otra URL → rojo. |
| 3 | `lib/api.test.ts::añade Authorization: Bearer con el token` | Con el interceptor registrado, una petición de `api` sale con la cabecera `Authorization: Bearer <token>` exacta. | Quitar el prefijo `Bearer ` o no asignar la cabecera → rojo. |
| 4 | `lib/api.test.ts::pide el token en cada petición` | Dos peticiones seguidas llaman dos veces a `getAccessToken`, y si el token cambia entre una y otra, la segunda lleva el nuevo. | Pedir el token una vez al registrar el interceptor y reutilizarlo → la segunda petición lleva el viejo → rojo. |
| 5 | `lib/api.test.ts::sin token la petición no sale` | Si `getAccessToken` rechaza, la llamada rechaza y el adaptador HTTP no recibe ninguna petición. | Envolver `getAccessToken` en `try/catch` y seguir sin cabecera → la petición sale → rojo. |
| 6 | `routes/RequireAuth.test.tsx::sin sesión no muestra la ruta privada` | Con `isAuthenticated: false`, el contenido hijo no se renderiza y se llama a `loginWithRedirect`. | Exportar `AuthGate` sin `withAuthenticationRequired` → el hijo aparece → rojo. |
| 6b | `routes/RequireAuth.test.tsx::con sesión muestra la ruta privada` | Control del 6: con `isAuthenticated: true` el hijo se renderiza y no se llama a `loginWithRedirect`. Sin él, una ruta mal montada también "ocultaría" el contenido y el 6 pasaría en falso. | Es un control, no se rompe: debe seguir verde cuando el 6 se pone rojo. |
| 7 | `routes/Me.test.tsx::muestra sub y role de /api/v1/me` | Con la API respondiendo `{ data: { sub, role } }` (contrato de §3.4), la página muestra ese `sub` y ese `role`. | Leer `res.data` en vez de `res.data.data`, o mostrar `id` en vez de `sub` → rojo. |
| 8 | `main.test.tsx::Auth0Provider pide un token para la API y usa refresh tokens` | El proveedor recibe `authorizationParams.audience` igual a `VITE_AUTH0_AUDIENCE` y `useRefreshTokens` verdadero. | Quitar `audience` o `useRefreshTokens` de `main.tsx` → rojo. |

> **El test 4 es el que protege de verdad.** Los tests 1-3 pasarían con cualquier implementación ingenua. El 4 caza el error que solo aparece una hora después del login, cuando vence el primer token.
>
> **El test 8 no mira `cacheLocation`, y es a propósito.** Afirmar el prop sería un duplicado más débil de `HU-04.md` test 4, que comprueba el efecto (el token no está en el storage). La casilla `ts-03.05` pide no repetirlo.
>
> **El test 7 es el único que debe nacer rojo hoy.** El tipo equivocado no se ve en tiempo de ejecución: `Me.tsx` vuelca la respuesta entera con `JSON.stringify`, así que el `sub` ya aparece dentro de un bloque `<pre>`. Para que el test detecte el drift, debe buscar `sub` y `role` como textos mostrados cada uno por su lado (coincidencia exacta), no dentro del JSON. Así nace rojo y pasa a verde con la corrección de §3.4.
