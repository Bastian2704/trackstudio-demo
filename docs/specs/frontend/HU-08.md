# HU-08 (frontend) — Registrar, editar y eliminar producciones

> **Jira:** `TS-19` · **Sprint:** 2 · **Cubre:** RF-02 (alta, edición y borrado), RNF-01 (control de acceso)
> **Contraparte:** [`../backend/HU-08.md`](../backend/HU-08.md)
> **Estado:** `[x]` borrador · `[x]` aprobada (2026-10-08) · `[ ]` implementada

Los criterios de aceptación de la historia viven en Jira. El contrato de la API (rutas, `ProductionResource`, errores) vive en la spec backend y aquí solo se referencia. Esta spec define las pantallas, el formulario, la confirmación de borrado, sus estados y cómo se traduce cada respuesta a la interfaz.

## 1. Alcance en esta capa

**Dentro:**

- Dos rutas solo para el productor: alta (`/artistas/:artistId/producciones/nueva`) y edición (`/producciones/:id/editar`).
- Un formulario compartido con `name` y `format`, validación mínima en el cliente y mapeo del 422 a cada campo.
- Precarga de la producción en la edición (`GET`), envío del alta (`POST`) y de la edición (`PUT`).
- Borrado (`DELETE`) desde la pantalla de edición, siempre tras un diálogo de confirmación.
- Estados visibles: cargando, enviando, eliminando, éxito, no encontrado y error.

**Fuera / diferido (con motivo):**

- **Selección del artista desde una lista → `TS-17` (HU-06). Apaño temporal:** como aún no existe un endpoint de listado de artistas, el artista del alta lo fija la URL anidada (`/artistas/:artistId/producciones/nueva`), igual que HU-05 se alcanza por URL. **TS-17 debe sustituir este apaño** por una selección/navegación real desde el listado de artistas y revisar si la ruta anidada se conserva. Decisión humana del 2026-10-08.
- Listado de producciones y navegación hacia estas pantallas → `TS-17` (HU-06). Hasta entonces se llega por URL.
- Reglas de formato por cantidad de canciones → `TS-20` (HU-09). Aquí solo se elige uno de los tres valores.
- Reasignar la producción a otro artista → inmutable por la spec backend §1. La edición no muestra ni envía `artist_id`.
- Mostrar el nombre del artista en el alta → requeriría una precarga extra que ningún criterio pide; el listado de TS-17 dará ese contexto.
- Mostrar fechas → no se pintan: la zona horaria de presentación sigue **ABIERTA** en D3.2.

## 3. Contrato técnico

### 3.1 Rutas

Se registran en `App.tsx` bajo `RequireAuth` y `RequireRole allowed={['productor']}`, junto a las de artistas.

| Ruta                                     | Página                 | Llamada a la API (backend §3.1)                       |
| ---------------------------------------- | ---------------------- | ----------------------------------------------------- |
| `/artistas/:artistId/producciones/nueva` | `ProductionCreatePage` | `POST /api/v1/productions`                            |
| `/producciones/:id/editar`               | `ProductionEditPage`   | `GET`, `PUT` y `DELETE /api/v1/productions/{id}`      |

- Los módulos son `src/routes/productions/ProductionCreatePage.tsx` y `src/routes/productions/ProductionEditPage.tsx`, con export default (`frontend/docs/nomenclatura.md` §3).
- El cliente **no valida** que `:artistId` ni `:id` sean UUID ni que el artista exista o esté habilitado: lo decide el backend (422 en el alta, 404 en la edición; §3.5).
- Un `artista` nunca ve estas pantallas: `RequireRole` lo manda a `/403`. Un 403 de la API lo resuelve el interceptor de HU-04.

### 3.2 Pantallas y textos

Esta spec es la dueña de los textos de la interfaz de HU-08.

| Elemento                         | Alta                     | Edición                                                                                       |
| -------------------------------- | ------------------------ | --------------------------------------------------------------------------------------------- |
| Encabezado (`h1`)                | «Registrar producción»   | «Editar producción»                                                                           |
| Campos (con `label` asociado)    | «Nombre», «Formato»      | «Nombre», «Formato»                                                                           |
| Botón de envío                   | «Registrar»              | «Guardar cambios»                                                                             |
| Botón de borrado                 | —                        | «Eliminar producción»                                                                         |
| Aviso de éxito (`role="status"`) | —                        | «Producción registrada.» (al llegar desde el alta) · «Cambios guardados.» (tras un `PUT`)     |

- **Formato:** un `<select>` nativo con una opción vacía «Selecciona un formato» y tres opciones, en este orden: «Sencillo» (`sencillo`), «EP» (`ep`), «Álbum» (`album`). El valor enviado es siempre el valor backed del enum (backend §3.6).
- El formulario es un único componente, `ProductionForm`, que usan las dos páginas. Lleva `noValidate`.
- No se muestran `id`, `artist_id` ni fechas.

**Diálogo de confirmación** (`role="alertdialog"`):

| Elemento          | Texto                                          |
| ----------------- | ---------------------------------------------- |
| Título            | «¿Eliminar producción?»                        |
| Descripción       | «La producción dejará de estar disponible.»    |
| Botón de confirmar | «Eliminar»                                    |
| Botón de cancelar | «Cancelar»                                     |

- Cancelar cierra el diálogo sin petición.
- Mientras el borrado está en curso, el diálogo no se cierra: ni «Cancelar» ni Escape.
- Tras un error de borrado, el diálogo se cierra y el aviso de error queda en la página (§3.5).
- Tras un 204 se navega a `/artistas/{artist_id}/editar` (el `artist_id` de la producción cargada) con el aviso «Producción eliminada.», que `ArtistEditPage` ya pinta en `role="status"`.

### 3.3 Validación en el cliente (Zod)

Solo adelanta lo obvio. El servidor es la fuente de verdad (backend §3.3).

| Campo    | Regla en el cliente                        | Mensaje                       |
| -------- | ------------------------------------------ | ----------------------------- |
| `name`   | Obligatorio (vacío tras recortar = falta)  | «El nombre es obligatorio.»   |
| `format` | Uno de `sencillo`, `ep`, `album`           | «Selecciona un formato.»      |

- **No** se valida el máximo de 255 ni la unicidad por artista: viven en el backend (mismo criterio anti-drift que HU-05 §3.3).
- Si hay errores de cliente, **no se envía ninguna petición**.
- Un campo con error lleva `aria-invalid="true"` y su mensaje visible debajo.

### 3.4 Datos (TanStack Query + `api`)

- Todas las llamadas usan `api` de `src/lib/api.ts`.
- Cuerpos exactos: `POST` → `{ artist_id, name, format }`, con `artist_id` tomado de la URL; `PUT` → `{ name, format }` (sin `artist_id`, backend §3.1).
- Tipo `Production` con la forma de `ProductionResource` (backend §3.7). La envoltura `data` se quita en la función de consulta o de mutación.
- **Precarga:** `useQuery` con clave `['productions', id]`. El formulario y el botón de borrado no se pintan hasta tener los datos; mientras tanto, «Cargando…».
- **Alta:** `useMutation`. Con el 201, se guarda la respuesta en `['productions', id]` y se navega a `/producciones/{id}/editar` con el estado de navegación que dispara «Producción registrada.».
- **Edición:** `useMutation`. Con el 200, se actualiza `['productions', id]` y el formulario muestra los valores devueltos por el servidor.
- **Borrado:** `useMutation`. Con el 204 se navega según §3.2. No se limpia la caché a mano: si se vuelve a la URL, la consulta se repite, recibe 404 y muestra «Producción no encontrada»; la entrada inactiva la libera `gcTime`.
- **Envío o borrado en curso:** el botón correspondiente («Registrar»/«Guardar cambios» o «Eliminar» del diálogo) queda deshabilitado; un segundo clic no genera otra petición.

### 3.5 Errores (por `code`, D3.1)

| Situación                                                      | Qué se muestra                                                                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 422 `VALIDATION_ERROR` con `errors.name` / `errors.format`     | El **primer mensaje** de cada campo, tal como llega, en ese campo. Se conservan los valores escritos.        |
| 422 `VALIDATION_ERROR` con `errors.artist_id`                  | El **primer mensaje** de `errors.artist_id`, tal como llega, en un aviso general (`role="alert"`). Cubre artista inactivo, inexistente, borrado o id no UUID (backend §3.4 y §3.8). Se conservan los valores. |
| 422 `VALIDATION_ERROR` sin ninguna de esas claves              | Aviso general: «Revisa los datos del formulario.»                                                            |
| Precarga con 404 `RESOURCE_NOT_FOUND`                          | Encabezado «Producción no encontrada», **sin formulario ni botón de borrado**.                               |
| Precarga con cualquier otro error                              | «No se pudo cargar la producción.», sin formulario ni botón de borrado.                                      |
| Envío con cualquier otro error (500, red, 404 en `PUT`)        | Aviso general: «No se pudo guardar la producción. Inténtalo de nuevo.» Se conservan los valores.             |
| Borrado con cualquier error (500, red, 404)                    | Se cierra el diálogo y aparece el aviso general en la página: «No se pudo eliminar la producción. Inténtalo de nuevo.» La pantalla de edición se mantiene. |
| 401 / 403                                                      | Nada propio: los resuelve el interceptor de HU-04.                                                           |

- Ninguna rama mira `message`, `title` ni `detail`; solo `code`, el estado de la respuesta y las **claves** de `errors`.
- Los textos de `errors.<campo>` llegan en español desde la API (backend §3.3). El frontend no los traduce.

## 5. Notas de implementación (para el humano)

- **Reutilizar:** `api` y `ApiErrorBody` (`src/lib/api.ts`); `Button`, `Input` y `Label` de `components/ui/`; la estructura de `routes/artists/` (`artistApi.ts`, `artistSchema.ts`, `ArtistForm.tsx`, páginas) como plantilla de `routes/productions/`.
- **Componente nuevo de shadcn:** `npx shadcn add alert-dialog` (estilo `base-nova`, primitivas de `@base-ui/react`). Es código de aplicación: lo ejecutas tú. Para el formato basta un `<select>` nativo con las clases de `Input`; no hace falta `shadcn add select`.
- **Orden sugerido de Green:** rutas en `App.tsx` (#18) → `productionSchema` + `ProductionForm` (#2–#4) → `ProductionCreatePage` (#1, #8) → errores del alta (#5–#7, #9) → `ProductionEditPage` precarga/edición (#10–#13) → borrado con diálogo (#14–#17).
- **422 → campos:** igual que `ArtistForm`, pero con `FIELDS = ['name', 'format']` y una rama previa: si existe `errors.artist_id?.[0]`, ese texto va al aviso general (#6). No extraer un helper común con `ArtistForm` por solo dos usos.
- **Tras borrar:** el `artist_id` sale de `query.data`. Navega con `` navigate(`/artistas/${artist_id}/editar`, { state: { notice: 'Producción eliminada.' } }) ``: `ArtistEditPage` ya lee `state.notice`.
- **Doble borrado:** deshabilita «Eliminar» con `isPending` de la mutación de borrado. El diálogo es controlado (`open`/`onOpenChange`): `onOpenChange` rechaza el cierre mientras `isPending` (Escape) y `onError` lo cierra.
- **Trampa:** con `<select>`, React Hook Form registra `''` para la opción vacía; el esquema Zod debe rechazarla con «Selecciona un formato.» (no con el mensaje por defecto de `z.enum`).
