# HU-11 (frontend) — Listar canciones con estado y posición

> **Jira:** `TS-22` · **Sprint:** 3 · **Cubre:** RF-03 (listado), RNF-01 (control de acceso)
> **Contraparte:** [`../backend/HU-11.md`](../backend/HU-11.md)
> **Estado:** `[x]` borrador · `[x]` aprobada (2026-10-19) · `[x]` implementada (2026-10-19)

El criterio de aceptación de la historia (listado con estado vigente y posición asignada) vive en Jira. El contrato de la API (ruta, orden, paginación, `SongResource` y errores) vive en la spec backend y aquí solo se referencia. Esta spec define dónde se pinta el listado, sus estados y cómo enlaza cada canción.

## 1. Alcance en esta capa

**Dentro:**

- Una sección «Canciones» dentro de `ProductionEditPage` (HU-08), con las canciones vigentes de la producción en el orden que da el servidor: posición, nombre (enlazado a su edición) y estado.
- Estados visibles: cargando, vacío, error y paginación cuando hay más de una página.
- Sustituye el apaño de navegación de HU-10 (frontend HU-10 §1, `HANDOFF_v25` §3.2): cada canción queda enlazada desde la producción.

**Fuera / diferido (con motivo):**

- Reordenar canciones → no hay endpoint (backend §1).
- Filtros, búsqueda y orden elegido por el usuario → el backend no los admite (backend §3.1).
- Número de versiones o última versión por canción → `versions` nace en `TS-24` (HU-13).
- Borrar desde el listado → `TS-23` (HU-12). El borrado sigue en la edición de la canción (HU-10).
- Listado para el artista → HU-21 (S6). Hoy la pantalla es solo del productor.
- Fidelidad visual con Figma → `TS-72` (S4). Aquí la sección usa los mismos componentes y clases que el resto de pantallas.
- Fechas → no se pintan: la zona horaria de presentación sigue **ABIERTA** en D3.2.

## 3. Contrato técnico

### 3.1 Dónde vive

- Componente nuevo `SongList` en `src/routes/songs/SongList.tsx` (export default), con una sola prop: `productionId`.
- `ProductionEditPage` lo monta **solo en la rama con la producción cargada**, después del enlace «Nueva canción» y antes de «Eliminar producción». Si la producción no carga (404 u otro error), no se pinta ni se pide el listado.
- No hay ruta nueva: la sección hereda `RequireAuth` y `RequireRole(['productor'])` de `/producciones/:id/editar`.

### 3.2 Textos y estructura

Esta spec es la dueña de los textos de la sección.

| Elemento | Texto |
| --- | --- |
| Encabezado (`h2`) | «Canciones» |
| Cargando | «Cargando canciones…» |
| Vacío (`meta.total = 0`) | «Esta producción aún no tiene canciones.» |
| Error (`role="alert"`) | «No se pudo cargar el listado de canciones.» |
| Resumen (solo con más de una página) | «Mostrando {from}–{to} de {total} canciones» |
| Paginación (solo con más de una página) | Botones «Anterior» y «Siguiente» |

**Tabla** con tres columnas, en este orden:

| Encabezado de columna | Contenido |
| --- | --- |
| «Posición» | `position`, tal como llega |
| «Canción» | `name` como enlace a `/canciones/{id}/editar` |
| «Estado» | Etiqueta de `STATUS_LABELS` («Por hacer», «En progreso», «Finalizada») |

- Las filas salen en el orden de `data`. El cliente **no reordena**: el orden total (`position`, `id`) es del servidor (backend §3.3).
- No se muestran `id`, `production_id` ni fechas.
- El nombre se pinta como texto de React (frontend `CLAUDE.md` §4).

### 3.3 Paginación

- La página es **estado local** de `SongList` (`useState`, empieza en 1), no un parámetro de la URL: la URL es la de la producción y un álbum con más de 15 canciones es el único caso que pagina (backend §3.3).
- Con `meta.last_page = 1` no se pintan resumen ni botones (sencillos y EP caben siempre en una página).
- «Anterior» deshabilitado en la página 1; «Siguiente» deshabilitado en la última.
- Cambiar de página pide `?page=N` y reemplaza las filas.

### 3.4 Datos (TanStack Query + `api`)

- Función nueva en `songApi.ts`: `fetchSongs(productionId, page)` → `GET /api/v1/productions/{productionId}/songs` con `params: { page }`. Devuelve la respuesta completa (`data` y `meta`), sin quitar la envoltura, como `fetchArtists`.
- Tipo `SongPage` en `songSchema.ts`: `{ data: Song[]; meta: { current_page; last_page; from; to; total } }`, con la forma de `ArtistPage`.
- `useQuery` con clave `['songs', 'list', productionId, page]`.
- ~~No se invalida la caché a mano tras alta, edición o borrado: al volver a la producción, la consulta se monta de nuevo y TanStack la vuelve a pedir.~~ **Corregido el 2026-10-21 (HU-09 frontend §3.5):** con `staleTime: 30_000` (`src/lib/queryClient.ts`), TanStack no vuelve a pedir una consulta fresca al montarla. El alta y el borrado de canciones invalidan `['songs', 'list', productionId]`. La edición del estado sigue sin invalidar: es un residual registrado en HU-09 frontend §3.5.

### 3.5 Errores (por `code`, D3.1)

| Situación | Qué se muestra |
| --- | --- |
| Cualquier error del listado (404, 500, red) | «No se pudo cargar el listado de canciones.» El resto de `ProductionEditPage` (formulario, «Nueva canción», «Eliminar producción») sigue visible. |
| 401 / 403 | Nada propio: los resuelve el interceptor de HU-04. |

- El 404 del listado solo ocurre si la producción se borra entre la precarga y el listado. No tiene texto propio: la producción ya se cargó y el aviso genérico basta.

- **Plantilla:** `ArtistListPage` (HU-06) para la tabla, los estados y la paginación. Diferencia: la página va en `useState`, no en `useSearchParams` (§3.3).
- **Reutilizar:** `api`, `STATUS_LABELS` y `Song` de `songSchema.ts`, `Button` de `components/ui/`. Nada nuevo que instalar.
